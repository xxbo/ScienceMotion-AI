# P1.1 — Two-topic creative-loop evidence

This deterministic acceptance scenario creates two silent, 12-second videos from empty projects through the public Creative Host tools. It covers creation, model/browser inspection, seeded defects, targeted edits, preview/export, persisted history, restart and snapshot restoration. The reference briefs and edits are scripted; this is not the real AI trial or human visual acceptance.

## Reproduce and inspect outputs

Use Node.js 22 (the CI version), FFmpeg/ffprobe, Noto CJK fonts and Remotion's headless browser:

```bash
npm install
npx remotion browser ensure
npm run typecheck
npm test
npm run accept:creative-loop
```

The runner is `scripts/creative-loop-acceptance.ts`; topic data and the test extension live in `scripts/fixtures/`. CI runs it after browser setup and uploads `creative-loop-evidence`, including failure traces if the scenario fails. Nothing writes generated topic components or mutates project files behind the Gateway. Filesystem reads in the runner independently verify published bytes.

| Output in `out/creative-loop/` | Evidence |
| --- | --- |
| `evidence.json` | CI source SHA, inventory, snapshot/revision/hash receipts, inspection coverage/costs, defects and edit/restore comparisons |
| `tool-calls.json` | Discovered-version invocations, inputs/results, diagnostics, project/run/call IDs, retry keys and call wall times |
| `plugin-transitions.json` | Exact plugin choices, before/after locks/manifests, failed upgrades and resumed usable versions |
| `*-manifests.json`, `*-executions.json` | Granted tool schemas/plugin versions and persisted host execution history |
| `{cache,water}-loop-{baseline,edited,restored}.mp4` | Six complete exports, each 960×540, 30 FPS, 360 frames / 12 seconds |
| `*-{0,90,359}.png`, `*.props.json` | Eighteen before/after/restored previews and their exact project documents |

Temporary host storage is removed after each run; CI evidence retains the documents, manifests, results and byte hashes needed for review. CI artifacts have GitHub's retention period; the existing 30-second narrated showcase remains the persistent public example.

## Fixtures and boundaries

| Topic | Two data-driven shots | Targeted change |
| --- | --- | --- |
| Cache hit/locality | Return data from cache; reuse recently accessed data | Clarify the explanation, move its text box and make the returning marker reach an earlier position at frame 90 |
| Evaporation/precipitation | Water enters the air; cooling/condensation and possible precipitation | Clarify liquid-to-vapor wording, move its text box and advance the rising marker at frame 90 |

Both use the same scene/text/shape/path/keyframe tools and generic Project Graph renderer. Neither adds topic-specific TSX. The paths and particles are schematic reference content, not physically calibrated simulations or independently reviewed scientific claims.

The trusted `acceptance.brief.attach` plugin uses only existing `CreativeServices` to store a JSON brief as a content-addressed data Artifact and add/replace the project's `approved-brief` asset. Two different brief payloads share the same asset ID. Restoring must recover the original payload and hash, so dependency restoration is not an empty-assets test. This extension is an acceptance fixture, not a general image/audio importer.

Inventory is reported separately: 19 executable built-ins, 1 executable extension with one active version, 1 catalogue-only manifest, and 300 synthetic entries exercised by the separate `accept:catalogue-scale` scenario. This creative-loop runner itself installs no synthetic scale entries; its evidence keeps that local count at zero. The session grants 17 tools needed by the workflow.

The extension now has v1/v2 and an intentionally unhealthy v3. Both topics create their original brief using v1, activate v2, reject the v3 upgrade with unchanged project/selection, then execute v2 to replace the data dependency. The second topic explicitly switches back to v1 for its baseline. After export, the application closes/reopens with its selected v2 factory and compares the exported version lock. [Host switching and scale details](P1.1-PLUGIN-SWITCH-SCALE.md) describe drain, grants, exact tool versions and explicit restart configuration.

## Assertions and scope of evidence

1. Discover manifests, invoke exact versions, create scenes/objects/tracks, save and inspect snapshots. Host/Gateway validation and independent canonical hashes check the boundaries.
2. Inspect baseline, seeded, edited and restored snapshots. I1 checks frames `0,45,90,135,179,180,225,270,315,359`; I2 measures frames `0,90,179,180,270,359` in the production browser after fonts load. Explicit coverage leaves other frames unchecked.
3. Seed two defects per topic: an intermediate animation key outside the viewport and an undersized text allocation. Assert the expected node/frame diagnostics, then repair using the approved edit. Four deliberately seeded defect instances must be detected, with zero misses among those instances only. Clean reports do not establish general defect recall or final visual quality.
4. Reject a stale-revision patch with no mutation, apply a valid patch, then replay its idempotency key before and after host restart without another revision. Compare unrelated nodes, tracks, scenes and shots. Marker pixels at frame 90 must match the requested center within one pixel and move by more than 30 pixels; the text region must change by more than 100 pixels; unrelated heading pixels remain identical.
5. Fully decode all six MP4s with FFmpeg, reject decoding failures/black intervals and check codec, size, FPS, frame count and duration with ffprobe. Check Artifact hashes. These fixtures deliberately contain no audio; they make no narration/caption-sync claim.
6. Close/reopen the production host and renderer, check history/idempotency persistence and old-snapshot immutability, then restore the baseline through the public tool. Canonical comparison omits only `project.updatedAt` and the revision list; all other project content, including assets, must match. The new audit revision must append to the edited revision and name the baseline snapshot hash. Full snapshot hashes should differ because audit history is preserved.
7. Verify the restored original data bytes/hash, identical sampled inspection frames, exact decoded PNG pixels at frames `0,90,359`, and six decoded MP4 frames at `0,90,179,180,270,359`. PNG tolerance is zero; MP4 tolerance is maximum channel difference ≤ 8 and mean channel difference ≤ 0.5 per sampled frame. This is within-run evidence, not a cross-platform MP4 byte-identity guarantee.

Invocation wall times include Gateway validation/persistence. I2 also reports browser measurement time and frames. Across the two topics the eight inspection pairs use 80 I1 frame projections and 48 I2 browser frames; inspection itself encodes zero images and makes zero visual-model calls. The separate output regressions encode 18 preview PNGs and six complete videos. Timings are observations for the current machine, not an efficiency target or a comparison against screenshot-based AI review.

## Render receipt regression found by the scenario

The edited fixture's unchanged second shot can produce the same PNG blob as its baseline. Previously, content deduplication returned first-writer metadata, incorrectly identifying the old snapshot/revision. Restoration exposed the same issue.

The fix keeps immutable CAS bytes/first-writer records and returns current invocation metadata/provenance in the render receipt. `creative-render-receipts.test.ts` tests PNG/video deduplication across frames, edited snapshots, separate projects and restart. The production scenario independently checks every render's requested snapshot hash, revision and frame/range. See [render service semantics](P1.1-G-RENDER-SERVICES.md).

## What remains for P1.1

The [acceptance checklist](P1.1-ACCEPTANCE.md) has 20/25 closed items after the host-switch/scale increment. The remaining five items form two work packages:

- A thin local interface for an AI client, one recorded real model creation/revision trial using discovered schemas and diagnostics, and the deterministic scenario retained alongside that trial.
- Final human review of both outputs, covering content, legibility, clipping/overlap and motion. The user explicitly deferred this review until final acceptance; automated checks do not close it.

General autonomous critique, broad media importing/audio/captions, worker isolation and advanced 3D remain later roadmap items. Do not expand P1.1 merely to increase tool or test counts.
