# P1.1-E — Local plugin version management

Last updated: 2026-11-14

## Scope and status

Implemented on top of the existing registry and gateway. This is a trusted, single-process plugin manager, not a third-party package installer or sandbox. This stage does not close P1.1.

Before this change, full CI #43405266507 passed on commit `64eb191e08d1b633b6ce69927cf631ea2a090161`. The new focused tests have been compiled and run locally; full repository and render acceptance is tracked by the workflow associated with the commit containing this document.

## APIs

| API | Contract |
| --- | --- |
| `install(plugin)` | Install an exact plugin version without publishing its tools; duplicate ID/version is rejected |
| `enable(id)` | Keep the active version, otherwise use a pin, otherwise choose the highest installed stable version |
| `activate(id, version)` | Explicit upgrade/downgrade to an installed version; dependencies, compatibility and pins must permit it |
| `rollback(id)` | Reactivate the previous active version through the same checks |
| `pin(id, version)` / `unpin(id)` | Lock/unlock the version; a pin must match an already active version |
| `getStatus(id, version?)` / `list()` | Inspect isolated status copies and all installed versions |
| `disable(id)` | Remove only the currently active, manager-owned registrations |
| `uninstall(id, version?)` | Remove an inactive, unpinned version; preserve dependency protection |
| `diagnoseDependencies(id, version?)` | Report missing/inactive dependencies, incompatible versions, breaking dependent upgrades and reachable cycles |
| `exportLock()` / `importLock(lock)` | Serialize exact choices; validate and atomically apply pins for already installed plugins |

Multiple versions can be installed, but only one version per plugin ID is exposed in the live registry. This avoids accidentally selecting a new implementation just because it was installed. The registry and gateway API are retained.

## Version grammar

Supported plugin versions are stable `MAJOR.MINOR.PATCH` with non-negative safe-integer components and no leading zeros. Supported dependency ranges are `*`, exact versions, caret ranges and tilde ranges with all three components. Unsupported syntax is rejected, never guessed.

Examples: `^1.2.3` excludes `2.0.0`; `^0.2.3` excludes `0.3.0`; `^0.0.3` permits only `0.0.3`; `~1.2.3` excludes `1.3.0`. These bounded rules follow the corresponding [node-semver conventions](https://github.com/npm/node-semver#caret-ranges-123-025-004). Prereleases, build metadata, wildcard components and compound/comparator ranges remain outside this implementation.

The JSON manifest schema and runtime use the same supported grammar. Catalogue validation identifies plugins by ID **and version**. `projectSchemaVersions` can be declared on a plugin or its tools; activation checks both against the manager's configured Project Schema version.

## Switching and failure handling

1. Validate the requested version, pin, active dependencies, enabled dependents and project compatibility.
2. Run the candidate's read-only health check while the old tools remain available. Default deadline is five seconds; the host can configure it.
3. Recheck registration ownership after asynchronous work.
4. Replace registrations synchronously. On registration failure, remove partially registered candidate tools and restore old registrations.
5. Publish the active version and status only after replacement succeeds.

The manager rejects lifecycle mutations with `PLUGIN_BUSY` while a switch is in flight. It does not queue them. Failed candidates are not exposed before health validation. Failed-plugin disable cannot unregister a foreign tool that caused its registration conflict.

This rollback restores registry selection, not external files, project mutations or side effects performed by plugin code. Health checks must be read-only. A health-check timeout stops waiting; it does not terminate non-cooperative JavaScript. Isolation and forced termination belong to P1.2. Calls already holding an old implementation may finish on that implementation; new calls see the new selection.

## Version locks

A lock contains `schemaVersion`, `projectSchemaVersion` and a plugin-ID-to-exact-version map. `schemas/plugin-lock.schema.json` defines its wire format. Export includes active and explicitly pinned selections. Import validates installation, project compatibility, dependency closure, cycles and active-version consistency before replacing the pin map.

The host saves/loads the returned JSON. Import does not download code, install missing versions or activate plugins. Code integrity/signature verification, persisted lock storage, automatic dependency solving and atomic multi-plugin upgrade plans are future work.

## Verification

- 18 focused tests cover version boundaries, multi-version activation, pins, explicit rollback, health failure/timeout, partial registration rollback, dependency safety, cycles, compatible locks, mutation isolation and uninstall behavior.
- Two repository integration tests exercise the real Registry/Gateway and the manifest/lock JSON Schemas.
- Existing plugin lifecycle tests remain unchanged and run alongside the new suite in CI.
- A local differential check compared 12,288 supported version/range combinations against the installed node-semver reference with no mismatches. This is a local check, not an added CI dependency.
- Documentation identity tests prevent README/architecture from silently becoming copied test code or another document.
