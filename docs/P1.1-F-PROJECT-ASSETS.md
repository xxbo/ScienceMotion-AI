## Versioned asset operations

The existing `ProjectPatchDocument` now accepts protocol `1.1.0` (existing node operations) and `1.2.0` (node operations plus `add-asset`, `replace-asset`, `remove-asset`). Asset operations with protocol 1.1.0 are rejected. The persisted `ProjectDocument` stays at 1.1.0; this is an explicit Patch protocol extension, not an implicit project-format migration. Old node patches remain valid. The schema validator exercises both versions and rejects undeclared cascade behavior.

Asset edits share the existing cloned-batch, revision conflict and duplicate-revision checks. IDs cannot change during replacement. Removal rejects assets used by clips, either end of dependency edges, or component `assetId`/`assetIds` fields (including nested payloads). Custom opaque references must declare dependency edges. There is no automatic cascade in this slice. Tools remove consumers explicitly first; the resulting asset batch cannot introduce dangling references.

Only canonical `artifact://sha256/<64 lowercase hex>` URIs are local dependencies. A matching `contentHash` is optional for such a URI; a contradictory hash is rejected. An external/local-file URI with a hash is not implicitly claimed by the Artifact Store. Reconciliation validates referenced bytes as well as metadata. URI/hash conflicts or missing/corrupt bytes do not authorize deletion of old references. Changed content under the same asset ID is reconciled by both owner role and artifact ID.

## Local workspace API

`FileSystemProjectWorkspace` implements the existing `ProjectRepository` interface and retains canonical `ProjectDocument`/`ProjectSnapshot` structures. Its additional methods are:

| Method | Meaning |
| --- | --- |
| `open(directory, lifecycle)` | Acquire an exclusive writer lease, validate the ledger and repair references before admitting work |
| `create`, `get`, `applyPatch` | Persist canonical projects with copied inputs/outputs and revisioned node/asset edits |
| `saveSnapshot(projectId, revisionId, metadata)` | Retain an immutable snapshot plus its local artifact dependencies; reject duplicate snapshot IDs |
| `getSnapshot(id)` | Verify retained dependencies before returning a copy for inspection/rendering |
| `restoreSnapshot(id, baseRevisionId, metadata)` | Restore content as a new revision on the current history; never reuse a historical revision ID |
| `releaseSnapshot(id)` | Explicitly remove retention for that snapshot through the same commit protocol |
| `collectGarbage(options)` | Collect through the shared lifecycle manager only while the workspace is healthy |
| `close()` | Drain workspace operations and release the writer lease; host stops Gateway admission first |

This is a small, single-writer JSON ledger for one local host, not a database or distributed workspace. Full projects and retained snapshots are stored together. Expensive large-project storage optimization is deferred until the creative path proves its need. Host schema validation remains required; structural/asset checks here do not replace the existing full project validator.

## Commit and recovery protocol

1. Clone/validate the next project state, enforce CAS, check consumers, and verify required local artifact bytes. Validation rejection leaves persisted state and references unchanged.
2. Persist an intent with old authoritative heads and the affected owners. The intent identifies a unique transaction.
3. Acquire durable temporary references for the proposed state's local artifacts. Existing project/snapshot references continue protecting the old state.
4. Atomically publish the new canonical heads and snapshot set, retaining the recovery intent.
5. Reconcile permanent references from the published state. Add required references before releasing stale ones; retain references for every remaining snapshot.
6. Release temporary transaction references and persist the clean ledger.

After any ambiguous publication or cleanup failure the instance fails closed: further mutations/GC require close/reopen. A thrown commit is not proof of rollback. Reopen reads the authoritative ledger, verifies all retained dependencies, repairs permanent references, removes only obsolete managed references, releases temporary pins and clears the intent. An uncommitted intent preserves the old head; a published head is preserved even when acknowledgement/cleanup failed. Callers inspect the persisted revision before a new invocation rather than blindly retrying with a new key.

Execution evidence and project state remain separate ledgers. This protocol protects projects/assets; it is not a distributed exactly-once effect guarantee or a transaction spanning every tool's external side effects.

## Ownership and retention boundaries

Workspace project roles are `workspace:<workspaceId>:asset:<assetId>`. Snapshot owner IDs include workspace/project/snapshot identities; temporary owner IDs include workspace/transaction identities. Cleanup never removes another workspace's roles or independent tool-run/user/plugin references. Related lifecycle instances sharing one reference-store object serialize their mutations with GC. All related host code must use that shared composition; multiple processes opening independent stores over the same artifact directory are unsupported.

File publication uses unique temporary files, file sync, atomic rename (or exclusive link for immutable objects), and directory sync on a POSIX local filesystem. Blob/reference writes no longer share a PID-only temporary name. Checksums detect accidental ledger corruption; they are not a security signature.

The writer lock is not automatically stolen after an abrupt host exit. Verify the old process is stopped, preserve the ledger/references, then explicitly remove a stale lock before reopening. Missing/corrupt retained dependencies fail closed without pruning reference evidence. Power-loss/network-filesystem guarantees beyond these primitives are not claimed by the tests.

Saved snapshots keep dependencies until explicitly released. Legacy standalone snapshot files are not automatically registered/imported into this workspace. Legacy detached-document lifecycle helpers remain compatibility utilities; persisted creative edits go through the workspace. Raw Artifact Store deletion still bypasses protection and must not be exposed to tools. Automatic GC scheduling, external-URI caching, distributed transactions and broad retention policy remain later work.
