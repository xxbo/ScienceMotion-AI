## Architecture and API changes

`LocalAgentToolGateway` remains the public tool entry point and retains Registry discovery and plugin selection. It delegates admission/execution to `LocalToolExecutor`; input/output JSON Schema checks and Artifact validation/retention stay in the Gateway adapter.

The internal `ToolExecutionStore` contract replaces `save/update` with:

- `reserve(startedRecord)`: atomically acquire the call ID and optional idempotency identity, or return the existing record without modifying it.
- `finish(terminalRecord, ownerToken)`: require the reservation's owner token, unchanged identity and a still-started record. Terminal records cannot be overwritten.
- `getByIdempotencyKey` and `list(projectId?)`: return isolated copies of recorded evidence.

Custom storage adapters must implement these atomic/ownership semantics; a read-then-write emulation is not equivalent. Existing built-in consumers were migrated together. This is a local storage boundary, not a claim of exactly-once distributed side effects.

## Invocation identity and concurrency

Idempotency identity is an unambiguous JSON tuple of project ID, tool ID, tool version and caller key. Call identity is a JSON tuple of project/run/call IDs. Delimiter characters in IDs cannot alias another tuple. Tools must declare idempotency before using a key; a change in tool behavior must receive a new tool version.

Canonical hashing accepts finite, acyclic JSON values and sorts object keys. Inputs and call context are copied before asynchronous admission. The pending entry is published before the first await; pending and stored duplicate requests both check the input hash. Identical pending calls share execution but receive isolated result copies. A follower cancelling its wait does not cancel the owner.

Gateways using the same store object share pending calls and concurrency counts. The store independently enforces reservation ownership. Admission rejection never finalizes somebody else's execution. Capacity is released after actual underlying work settles, including non-cooperative work that outlives a timeout. The host must share its store and a consistent execution policy across related gateways.

## Outcomes, retry and shutdown

Recorded states: `started`, `succeeded`, `failed`, `cancelled`, `timed-out`, `interrupted`. Timeout returns `TOOL_TIMEOUT`, separately from `TOOL_CANCELLED`. Exceptions or cancellation after execution begins conservatively mark `metadata.outcomeUnknown`; this is not proof that effects were rolled back.

Only persisted successful results are replayed as success. Terminal failed keys remain consumed. Interrupted/uncertain keys return `TOOL_RECOVERY_REQUIRED`; the host reconciles project/external effects before choosing a new invocation identity. A failed terminal write returns `TOOL_EXECUTION_STORE_FAILED`, not a successful response. A previous `started` record remains reserved if final evidence could not be confirmed.

Retries remain limited to declared-idempotent tools returning explicitly retryable results, at most five attempts. Each attempt receives a fresh input copy. The deadline spans the admitted execution/inspection/retry window. Cancellation during storage admission is observed before any tool starts once the storage operation settles; the storage operation itself is not forcefully cancelled. Observation hooks are best-effort and cannot turn a committed success into a failure.

`gateway.shutdown()` stops that gateway's admission and waits for underlying work to settle, including timed-out calls. Stop all gateways sharing a store before closing it. Non-cooperative JavaScript can delay draining; forced termination belongs to P1.2 workers.

## FileSystemToolExecutionStore

The optional backend writes a versioned, checksummed local JSON ledger. It uses a unique temporary file, file sync, rename and directory sync before publishing state in memory. A write/publish failure makes that store instance fail closed until reopened. Corrupt/unsupported ledgers are rejected rather than silently reset. The checksum detects accidental corruption, not malicious modification by a trusted-host administrator.

An exclusive `writer.lock` prevents a second writer opening the directory. Clean shutdown releases the lock. After an abrupt process exit the lock is deliberately not stolen: the host/operator first verifies the prior writer has terminated, preserves/inspects the ledger and only then removes the stale lock. Opening a ledger with unfinished `started` records converts them to `interrupted` and retains their idempotency identities. Temporary files are not accepted as successful ledger commits.

Example host composition (registry populated separately):

```ts
const store = await FileSystemToolExecutionStore.open(".local/executions");
const gateway = new LocalAgentToolGateway(registry, {
  executionStore: store,
  allowedPermissions: ["project.write"],
  maxConcurrentCalls: 16,
  maxTimeoutMs: 30_000,
});
try {
  // Discover and invoke installed tools with project/run/call IDs.
} finally {
  await gateway.shutdown();
  await store.close();
}
```

Gateway defaults grant no declared permissions, reject destructive/high-cost tools without explicit host configuration, cap total concurrent calls at 32, use a default per-tool limit of 8 and cap execution time at 30 seconds. `allowDestructive`/`allowHighCost` are trusted host configuration, not agent-controlled arguments or an approval UI. The first creative host now composes these services through `openCreativeHost()` with explicit project-bound session grants, plugin/tool permission intersection, destructive/high-cost approval, bounded limits and graceful drain. See [P1.1-F Creative Host](P1.1-F-CREATIVE-HOST.md).

## Creative host and editing integration

Patch protocol 1.3.0 adds scene, shot and animation track operations while ProjectDocument remains 1.1.0. The editing layer validates graph ownership, sequence/scene bounds, animation targets, duplicate active property tracks and supported interpolation. Linear, step and cubic-bezier easing are implemented; unsupported curves/easing are diagnosed rather than silently mapped to linear. See `creative-editing.test.ts` and [host assembly](P1.1-F-CREATIVE-HOST.md).

`openCreativeHost()` composes the filesystem workspace, shared artifact lifecycle/reference store, persistent execution ledger, exact pinned plugin versions, Registry and Gateway. It exposes project-bound sessions with explicit tool and permission grants. The built-in workspace plugin supplies project create/inspect, revisioned patch apply, separately approved removal, snapshot save/inspect/restore and execution history. Host services are scoped and re-check session, plugin and tool declarations on every use. Artifact reads verify project/invocation ownership and bytes; snapshot dependencies are retained. Shutdown stops admission, drains calls and service work, closes persistent resources and releases the single-writer lock. It is a trusted in-process local host, not a third-party sandbox or distributed transaction system.

`creative-host.test.ts` covers authorization, exact versions, project isolation, service capability expiry, async service drain, cancellation/timeout, graceful shutdown, artifact ownership/integrity, snapshot pinning and operation limits. `creative-host-integration.test.ts` exercises real filesystem composition across restart, idempotent replay, plugin health failure, exclusive lock, corruption handling and snapshot/artifact GC protection.

The built-in workspace plugin is not the G graphics/animation/render suite. Generic Project Snapshot rendering, two-topic fixtures, 10–12 executable creative tools, 300 synthetic catalogue tests, visual review and a real AI invocation trial remain P1.1-G/H acceptance work.
