# P1.1-G — Snapshot Render Services

## Public tool surface

- render.preview({ snapshotId, frame, sceneId? }) produces a PNG Artifact for one frame.
- render.video({ snapshotId, startFrame, durationFrames, sceneId? }) produces an H.264 MP4 Artifact for a bounded range (maximum 900 frames / 30 seconds at 30 FPS).

Both tools use the existing Plugin → Registry → Gateway → invocation-scoped CreativeServices path. The AI supplies a snapshot identity and frame parameters only; it cannot supply a filesystem path, output path, renderer executable or entrypoint.

## Trust and consistency boundaries

1. The host verifies the snapshot exists and belongs to the session project.
2. It validates the immutable document against Project Schema and verifies its canonical SHA-256 content hash.
3. It validates frame/range bounds against the snapshot's first sequence.
4. It renders a cloned snapshot document through the trusted ProjectGraphRenderer.
5. It checks output type, extension, byte length and renderer identity/version.
6. It stores bytes in the content-addressed ArtifactStore and constructs an invocation receipt: snapshot ID/hash, source revision, frame/range, dimensions/FPS and renderer identity/version.
7. The tool returns the Artifact reference and current render metadata. Gateway output validation verifies the content hash/URI, retains the Artifact under the current project/run/call and persists the result in execution history.

Identical output bytes share a blob, even when snapshots, frames or projects differ. The store keeps its immutable first-writer record, including its creation time. `CreativeServices.render` returns that blob identity with the **current invocation's** metadata and provenance; it does not use first-writer metadata as evidence for a later render. Cross-project first-writer metadata is redacted before the current receipt is attached. Consumers should use the render result/execution record for invocation evidence, not infer it from a CAS lookup.

Required permissions are snapshot.read and artifact.write, intersected across session, plugin and tool. Foreign-project snapshots, invalid hashes, out-of-range requests and oversized outputs fail before a successful Artifact is returned.

## Default renderer

RemotionProjectGraphRenderer uses the Remotion bundler and renderer APIs. It renders still PNG previews and H.264 MP4 ranges using the generic ProjectGraph composition. Composition metadata is derived from the supplied ProjectDocument sequence, so render duration, FPS and dimensions come from the immutable snapshot rather than the demo fixture.

The renderer can be replaced only by trusted application configuration, primarily for deterministic tests. Tool inputs cannot choose an implementation.

## Current boundary

The service is synchronous and local, with a 900-frame cap and the host's configured execution timeout/artifact byte limits. The [first P1.2 increment](P1.2-WORKERS.md) adds opt-in Linux render workers, progress callbacks and process-tree cleanup on cancellation/deadline. The host checks cancellation again before publishing returned bytes. Durable asynchronous jobs and resumable rendering remain open. Multi-sequence orchestration, transitions, audio/captions and visual review remain later creative-loop work.

## CI verification

The workflow runs a production-host smoke scenario: create/edit a project through tools, save a snapshot, render a PNG preview and MP4 video through render.preview / render.video, then validate PNG signature and MP4 streams/dimensions/FPS/duration with ffprobe.

`creative-render-receipts.test.ts` deliberately returns identical PNG/MP4 bytes for different requests and verifies current snapshot/revision/frame/provenance, public tool results, restart persistence and cross-project isolation while checking that stored metadata remains unchanged. The [two-topic creative loop](P1.1-CREATIVE-LOOP.md) exercises the same case with production pixels: an edit leaves the second shot unchanged, and a later restore reproduces the original frames under a new audit revision.
