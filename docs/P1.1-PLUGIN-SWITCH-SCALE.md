# P1.1 — Host plugin switching and catalogue scale

This increment closes Gate C's integrated switch/failure case and Gate X's 300-manifest scenario. It adds trusted application administration to the existing Creative Host and records scale evidence using the production registry. No new production creative tools or general autonomous agent are introduced.

## Administrative interface

| `host.plugins` API | Behavior |
| --- | --- |
| `install(factory)` | Validate and install an exact trusted implementation without publishing its tools |
| `activate(pluginId, version)` | Drain existing work, check the installed candidate and explicitly select that version; selecting an older installed version performs rollback |
| `list()` | Return statuses for installed versions, including failed candidates and the active pin |
| `exportLock()` | Return exact selected versions for the application to record and use when configuring the next host |

These methods are not AI tools or invocation-scoped services. The application supplies code through a `CreativePluginFactory`; no tool input accepts code, package names or paths. Administration from inside a tool invocation is rejected. The executable built-in tool count remains 19.

Installation applies the same identity/schema/permission/service wrapping as startup. Tool IDs remain reserved to their owning plugin across installed versions. Reusing a tool ID in another plugin version requires a distinct tool version; this prevents a stale exact-version request or idempotent retry from selecting another installed implementation. Plugin authors must preserve that identity convention when supplying code after restart as well. Installed identities cannot be silently overwritten.

## Transition and failure behavior

1. Enter `switching` synchronously. New sessions, discovery/invocations and maintenance return an explicit busy diagnostic; callers retry after the administrative operation finishes. Concurrent administrative changes are rejected.
2. Shut down the session gateways and wait for actual execution/service work to finish. A timed-out tool that is still running keeps the transition waiting. This is a cooperative local drain, not worker termination.
3. Use the existing plugin manager for dependency/project compatibility checks, bounded read-only health checks and synchronous registry replacement. On health failure, timeout or partial publication failure, preserve the old tools and active pin.
4. After a successful switch, refresh the host catalogue. Recreate gateways with the same session grants and limits, so new schemas are compiled without stale validators. Removed tools disappear; newly added IDs or additional permissions do not expand existing grants. Discovery detects a catalogue change across asynchronous pages and requires a retry.
5. Resume the same sessions. If close begins during the transition, wait for it and close resources without reopening admission.

The transition briefly pauses new work across the host. A health timeout stops waiting but cannot terminate arbitrary JavaScript; trusted health checks must remain read-only. Isolation belongs to P1.2.

The lock is descriptive JSON. It does not contain code, download packages, automatically persist installed versions or automatically load factories. The acceptance runner explicitly reopens with its chosen v2 factory and checks that the resulting selection equals the exported lock. Existing project/execution/snapshot storage remains durable; plugin code selection remains application configuration.

## Integrated creative evidence

`npm run accept:creative-loop` now exercises the following path on both cache and water-cycle fixtures:

- Create and attach the baseline brief through plugin/tool v1.
- Perform the existing stale-revision rejection, safe retry and targeted text/motion edit.
- Activate v2, attempt an unhealthy v3 upgrade, verify unchanged project/catalogue/selection on failure, then invoke v2 to replace the actual brief data dependency.
- Export the edited video, close/reopen with the explicit v2 selection, restore the old snapshot/dependency and compare original/restored pixels.

`out/creative-loop/plugin-transitions.json` and `evidence.json` preserve before/after locks and manifests, candidate statuses, diagnostics, timings and the implementation version that actually executed after failure. `tool-calls.json` records exact tool versions. The two topics also exercise an explicit v2→v1 rollback before creating the second baseline. CI uploads all of this in `creative-loop-evidence` alongside the six MP4s and 18 previews.

`creative-plugin-switch.test.ts` adds focused production-host coverage for schema changes, stale-version rejection, per-version idempotency/restart replay, rollback, unhealthy/timed-out candidates, partial registry rollback, dependency/compatibility rejection, session grants, removed/added tools, forbidden in-tool administration, timed-out work draining and close during preflight.

## 300-manifest scenario

Run `npm run accept:catalogue-scale`. The production registry receives **100 synthetic tool IDs × 3 versions = 300 manifests**, across five namespaces. Versions include `1.9.0` and `1.10.0` to exercise numeric ordering. The required implementation callbacks are non-executable guard stubs; the runner asserts zero synthetic executions.

Checks cover registration conflicts, nine pages of size 37 without omissions/duplicates, the 200-item page cap, exact/latest resolution, deprecated entries, text/category/tag filters, project compatibility, engine/capability combinations and unavailable capabilities. An incompatible plugin and a plugin conflicting with an existing registration must fail without changing the 300-entry catalogue.

CI writes `out/catalogue-scale-evidence.json` and uploads it in `sciencemotion-demo`. It records the CI source SHA, Node/OS/CPU/memory context, registration/pagination/resolution/conflict times, and p50/p95/max across 55 discovery queries. These are baseline observations, not latency guarantees; no timing threshold can make CI flaky. Capability/engine filtering establishes discovery behavior, not successful execution of unsupported engines.

Inventory remains separate: **19 executable built-ins, one executable brief extension with one active version, one catalogue-only JSON fixture, and 300 synthetic scale entries (100 IDs)**. v1/v2/v3 are versions of one extension; v3 is deliberately unhealthy. None of the synthetic entries represents a finished creative capability.
