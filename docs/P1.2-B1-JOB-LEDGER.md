# P1.2-B1 — Render job contract and durable ledger

Last updated: 2026-11-17

This describes B1 as delivered by [PR #10](https://github.com/xxbo/ScienceMotion-AI/pull/10), main `82281fc`, with [241-test main CI](https://github.com/xxbo/ScienceMotion-AI/actions/runs/44033946604). Its host/client integration is now implemented in [B2](P1.2-B2-HOST-JOBS.md); integration requirements below describe the boundary of the internal store itself.

## Delivered scope

B1 supplies versioned job types, validated transitions, executor ownership, project-scoped idempotent submission, bounded progress/results and a local filesystem ledger. It is an internal foundation for the [P1.2-B sequence](P1.2-PLAN.md), not an AI-facing asynchronous render API. The existing host, 19 built-in tools, local wire protocol and renderer behavior remain unchanged.

`RenderJobStore` is implemented by `InMemoryRenderJobStore` and `FileSystemRenderJobStore`. The filesystem implementation stores `jobs.json` under an application-selected directory and holds an exclusive `writer.lock`. IDs never select filesystem paths. Existing workspaces are not migrated or opened by this increment; B2 will compose this ledger into the host lifecycle.

Initial job operations are PNG preview and bounded MP4 video, corresponding to `render.preview` and `render.video`. Browser-layout jobs are not part of this initial job contract. B1 does not schedule workers, authorize client sessions, inspect snapshot bytes, retain assets, publish Artifacts or prove that an OS process has stopped. B2/B3 perform those actions before acknowledging the corresponding job transitions.

## Immutable request and receipt

`RenderJobSubmission` records project/submission/run/call identities, exact tool version, snapshot ID/revision/hash, operation and frame/range, optional scene, render dimensions/FPS and expected renderer ID/version. The host must supply these resolved values; they are not a wire schema allowing the AI to choose paths or executable code.

The canonical SHA-256 input hash covers the complete submission. The idempotency scope is the JSON tuple `[projectId, submissionId]`, preserving delimiter distinctions. Concurrent identical submissions create one queued job. The same identity and same input returns its existing record in any state, including terminal/interrupted states; changing any input field, including run/call provenance, conflicts. A deliberate new execution needs a new submission identity.

Records include schema version `1.0.0`, a generated job ID, monotonically increasing record revision, timestamps, bounded progress, stop/publication/interruption evidence and a terminal result or diagnostic. Returned records are copies. Every read/list/control operation requires an explicit project ID; B2 must derive that ID and permissions from the bound session. Project filtering is not itself session authorization.

A successful receipt binds its job ID and input hash to a content-addressed Artifact ID/hash, byte count, media type and expected renderer identity. The input hash transitively binds the snapshot, revision, profile and all parameters. B1 validates this declaration; B2 verifies the actual bytes and publication/reference evidence, with real worker/CLI regression in B3. The job record does not replace the tool-execution ledger or canonical Project Graph.

## State and ownership rules

| State | Meaning / permitted next step |
| --- | --- |
| `queued` | Durable metadata reservation, no executor ownership; claim it or stop it immediately |
| `running` | One executor owns an in-memory random token; progress, stop request, publication barrier or failure |
| `stopping` | Cancellation/deadline request persisted; first stop reason wins; wait for executor cleanup acknowledgement |
| `publishing` | Durable publication barrier; new stop requests return `accepted: false`; complete publication or record uncertain failure |
| `succeeded` | Published result declared by the trusted executor and bound to this job; terminal |
| `failed` | Executor failure; `outcomeUnknown: true` if publication had begun; terminal |
| `cancelled` / `timed-out` | A queued job was stopped without execution, or the owning executor acknowledged the matching stop after cleanup; terminal |
| `interrupted` | A previously active record was found on reopen; original state/evidence retained; terminal and never automatically replayed |

`claim` persists `running` before returning its token. Only that token can update progress, begin publication or finish the execution. Tokens never appear in records, disk files, list/query results or idempotent submission responses; reopening discards their authority.

`requestStop` takes `cancelled` or `timed-out`. For a running job it records `stopping`, without a completion timestamp. It cannot be reported as cleanup completion. An accepted stop blocks publication and success; a later stop preserves the first reason. A terminal job is immutable.

After the renderer has stopped and output is verified, the executor must await `beginPublication` **before** writing an Artifact. This barrier competes atomically with stop requests. If stop wins, publication fails. If publication wins, the stop response explicitly declines cancellation, allowing publication to settle consistently. `finish` then declares the verified published result, failure, or completed cleanup. These calls are trusted executor acknowledgements, not OS-process observation by the ledger.

## Persistence and reopening

The filesystem ledger reuses the repository's POSIX local publication helper: write a private temporary file, sync it, rename it over `jobs.json`, then sync the directory. In-memory state and acknowledgements are published only after that operation succeeds. An envelope checksum covers its schema version and records; loading also validates each record's identities, state relationships, timestamps and receipt bindings. Unsupported versions, duplicate IDs/submission keys and inconsistent records fail closed without overwriting the file.

Any ambiguous persistence failure rejects the operation and poisons further reads/writes until close/reopen. If terminal publication reached disk but its acknowledgement was lost, reopening returns that persisted terminal result. If disk still contains an active record, reopening durably converts it to `interrupted`, preserving progress, stop intent and the publication marker. Previously queued jobs have `outcomeUnknown: false`; previously claimed jobs conservatively have `outcomeUnknown: true`. Recovery never claims cleanup, rolls back Artifacts or automatically starts another render.

`close()` synchronously stops new ledger calls, drains admitted ledger operations and releases its own lock. It does not drain a renderer; the host/controller must do that first. An abandoned process leaves a lock and another open fails. B1 never steals a stale lock by PID inference. Trusted recovery must establish exclusive ownership and stop/reap the old work before removing an abandoned lease. The process-exit test removes only the lock of its own child after `spawnSync` confirms that child exited.

B1 used a single-writer filesystem ledger with terminal execution records. C2 layers explicit reconciliation and release evidence into the same ledger and supports deliberate compaction with submission identities preserved. [C2 retention administration](P1.2-C2-RETENTION.md).

## Bounds and progress

| Bound | Default / contract |
| --- | --- |
| Record count | `maxJobs: 1000`, configurable 1–10,000; full ledger rejects new identities without evicting existing ones |
| Ledger bytes | `maxLedgerBytes: 16 MiB`, configurable 1 KiB–64 MiB; includes reserved growth space for active jobs |
| Input / record / completion JSON | At most 16 KiB each, finite JSON and documented keys only |
| Active-record growth reservation | Reserve up to the full 16 KiB record cap at admission, so valid progress/terminal records fit even at capacity |
| IDs / diagnostic message | 128 UTF-8 bytes per identity; 2 KiB per diagnostic message |
| Progress persistence | Default 250 ms between same-phase changes, configurable 0–60,000 ms; phase changes persist immediately |
| Listing | Explicit project, offset, default 50 records and maximum 200 per page |
| Render declaration | Dimensions 1–7680, FPS >0 and ≤120; safe integer frames; video duration 1–900 frames |
| Result declaration | PNG/MP4 consistent with operation; 8 bytes–64 MiB; `sha256:` identity matches declared content hash |

Bounds on render declarations do not establish compatibility with a particular snapshot or renderer; the host must apply its actual sequence/profile limits. Ledger byte reservation is not a temporary-disk or total-render-memory budget. Configuring less than one active record's reserved space admits no new jobs.

Progress never regresses across phases or within a phase. Duplicate/throttled updates return `updated: false` and the last persisted record. Rejected/throttled progress does not advance its revision. Clock rollback is clamped within a job so timestamps remain ordered. The ledger stores the latest durable progress, not an unbounded frame-event history.

## Verification and next step

`npm test` includes 18 B1 tests covering concurrent duplicate submission and competing claims, project filtering, caller mutation isolation, cancellation/publication races, late results, deadline precedence, receipt mismatches, progress throttling and clock rollback, capacity with reserved completion space, persistence-before-acknowledgement, close/drain, reopening every active state, real child-process abandonment, checksummed/semantic corruption, failures before/after filesystem publication, actual rename failure, bounded/symlink reads and replacement-lock preservation.

These tests establish the contract and local persistence behavior. [B2](P1.2-B2-HOST-JOBS.md) subsequently composed the store into the host, authorized/retained inputs before client admission, and exposed submit/get/list/cancel. Its real-render smoke verifies successful PNG/MP4 jobs and persisted results; [B3](P1.2-B3-CLI-LIFECYCLE.md) now completes the worker/CLI cancellation and interrupted-host scenario. Human effect review remains in the final acceptance workstream.
