# P1.2-B2 — Host and local-client render jobs

Last updated: 2026-11-17

## Delivered scope

The host now opens [B1's durable job ledger](P1.2-B1-JOB-LEDGER.md) and exposes `session.jobs.submit/get/list/cancel`. The opt-in local protocol **1.1.0** exposes the same operations as `jobs.submit`, `jobs.get`, `jobs.list` and `jobs.cancel`; the job API/schema remains **1.0.0**. Submission persists a queued record and returns before rendering finishes. Queries and cancellation use the job ledger without waiting for that background render.

Jobs use the host-selected renderer, with the existing in-process default or trusted `renderWorker` option. B2 includes seventeen integration tests and a real in-process PNG/MP4 smoke scenario. The complete protocol-1.1 CLI workflow with Linux workers, mid-render cancellation, process cleanup and interrupted-host recovery is the next **B3** increment. Existing A worker regression is not evidence of that new end-to-end workflow.

These are native host operations with their own durable job evidence, authorized by the existing `render.preview` / `render.video` grants. They do not invoke plugin code or fabricate Gateway execution records. The 19 built-in tools and existing `invoke` execution ledger remain unchanged. The binding currently supports the built-in workspace's render tool version `1.0.0`; changing the selected implementation/version requires an explicit compatible job binding.

## Authority and input retention

The session supplies the project ID and authorization. A submit request supplies only a submission/run/call identity, exact discovered render tool version, snapshot ID and preview/video parameters. It cannot choose filesystem paths, a renderer, executable code, project authority, permissions or a timeout. Tool grants, declared permissions, cost/destructive approvals and the current exact version are checked before admission. Reads and cancellation require the matching render grant; listing filters unauthorized operations before pagination and does not count hidden jobs. Revoked sessions cannot query or control jobs. Another authorized session for the same project can observe or cancel them.

Admission is serialized with project maintenance. It verifies snapshot project/schema/hash/revision, sequence bounds and scene membership, and reads the workspace's retained snapshot with verified Artifact dependencies. Mutable external asset URIs are rejected for jobs. The persisted queued record pins the already-durable snapshot before the client acknowledgement; the workspace's snapshot references retain its local Artifact dependencies. Neither a second project model nor a copy of the snapshot document is stored in the job ledger.

`releaseSnapshot` refuses to remove snapshots used by active, interrupted or uncertain jobs. Normal terminal jobs allow explicit snapshot release; their idempotent submission still returns the original job even after release. Interrupted/uncertain jobs conservatively keep inputs for reconciliation. Automatic reconciliation, pruning and a retention administration API remain C work. GC cannot release a retained snapshot's dependencies. These are host-mediated guarantees in a trusted single-writer workspace, not protection against an operator editing its files behind the host.

An identical project/submission identity returns the original record. Different parameters or run/call provenance under that identity fail with `RENDER_JOB_CONFLICT`. Concurrent identical admissions share one persistence operation and return separate response copies. A retry never starts another render; deliberate re-execution needs a new submission identity.

## Lifecycle and execution limits

The initial runner executes one background job at a time in admission order. `renderJobs.maxActiveJobs` defaults to 8 (range 1–32), bounding running plus queued inputs. A second bound of the same size limits pending distinct admissions; duplicate in-flight submissions are coalesced. Overload rejects new admission with `HOST_JOB_CAPACITY` before reserving its identity. This small runner is not a fairness policy or an aggregate budget across synchronous tools and background jobs; C/D address those controls.

Long background renders run outside the canonical project queue. Admission and result publication remain serialized with project/Artifact maintenance. Project editing can continue while the job consumes its retained snapshot. Legacy synchronous render/layout invocations still occupy their original service queue and can delay admission/publication; synchronous `invoke` also remains blocking on the sequential wire. Clients should use `jobs.submit` for renders they need to control on that connection.

`renderJobs.timeoutMs` defaults to 30,000 ms (range 1–300,000), capped by the host limit and selected tool timeout. It starts when execution is claimed, includes waiting to begin publication, and stops at the durable publication barrier. The renderer's own deadline may be stricter. Queue waiting has no execution timeout. Progress uses a bounded coalescing observer plus B1's throttled persistence, so frame callbacks cannot accumulate an unbounded chain of writes.

Cancellation of a queued job is immediately terminal. Cancellation/deadline of a running job persists `stopping`, then signals the renderer; the job becomes terminal only after the renderer promise settles through cleanup. A renderer that ignores its signal delays terminal cancellation and close. Only the Linux worker supplies A's forced process cleanup; an arbitrary trusted injected renderer remains cooperative. Late output after an accepted stop is discarded. A cleanup failure preserves unresolved evidence and fails the host rather than claiming completed cancellation.

After cleanup and output identity/type/size validation, the executor persists `publishing` before storing an Artifact. Cancellation after this barrier returns `accepted: false`; session revocation or host close allows the committed publication to settle. The host verifies stored bytes/hash/receipt and retains the output before persisting success. A publication failure remains uncertain, with the input retained. Storage uncertainty fails further host admission and requires close/reopen; it is never acknowledged as success or automatically retried.

Revocation requests cancellation for jobs originally submitted by that session. Host close stops admission, cancels queued/running jobs, drains actual rendering/publication, and then releases resources. Plugin activation pauses admission and drains jobs before changing the catalogue. On normal reopen, terminal results remain queryable; B1 converts abandoned active records to `interrupted`. No stale locks are automatically removed and no interrupted render is automatically restarted.

## Local protocol 1.1

Launch configuration still has `schemaVersion: "1.0.0"`. Select protocol 1.1 explicitly; omission retains protocol 1.0 and its original ready message/methods. Historical transcripts and their replay are unchanged.

```json
{
  "schemaVersion": "1.0.0",
  "protocolVersion": "1.1.0",
  "directory": "workspace",
  "traceFile": "jobs-session.jsonl",
  "grant": {
    "projectId": "my-project",
    "permissions": ["project.read", "project.write", "snapshot.write", "snapshot.read", "artifact.write"],
    "toolIds": ["project.create", "project.inspect", "project.snapshot.save", "render.preview", "render.video"]
  },
  "renderJobs": { "maxActiveJobs": 4, "timeoutMs": 30000 }
}
```

Run `npm run --silent host:stdio -- --config /path/to/config.json`. After creating and saving an authorized snapshot through the existing tools, use:

```json
{"id":"submit","method":"jobs.submit","params":{"submissionId":"video-1","runId":"my-run","callId":"video-1","toolId":"render.video","toolVersion":"1.0.0","input":{"snapshotId":"saved-snapshot","startFrame":0,"durationFrames":30}}}
```

The response is `{id, ok: true, result: {created, record}}`. Use the returned `record.id` in subsequent requests; request IDs correlate wire replies and are separate from submission/job IDs.

| Method | Parameters | Result |
| --- | --- | --- |
| `jobs.submit` | Request above; preview uses `render.preview` and `{snapshotId, frame, sceneId?}` | `{created, record}`; video uses `{snapshotId, startFrame, durationFrames, sceneId?}` |
| `jobs.get` | `{jobId}` | Authorized job record, or `null` if absent/foreign |
| `jobs.list` | `{offset?, limit?}`; default 50, maximum 200 | `{jobs, total, offset, limit}` after grant filtering |
| `jobs.cancel` | `{jobId}` | `{accepted, record}`; `stopping` is not yet cancelled |

The 1.1 ready message includes `jobsVersion: "1.0.0"` and the four methods. Request/trace/output bounds and sequential backpressure remain as documented for [the local client](P1.1-AI-TRIAL.md#local-protocol). Job submissions have an additional 16 KiB JSON cap. A job receipt acknowledges durable admission, not success: poll until a terminal state and inspect the result or diagnostic. Keep the connection open while jobs run; EOF, close and signals revoke/cancel/drain the host. There is no detached daemon.

Trace/output loss after submit/cancel can lose an acknowledgement after persistence. The transport reports uncertainty where possible, stops later dispatch and drains. Query the job or repeat its original submission identity after reopening; do not invent a new identity merely because a response was lost.
