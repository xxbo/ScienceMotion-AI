# P1.2-B3 — Real CLI job cancellation and host interruption

Last updated: 2026-11-17

## Delivered scope

B3 completes [P1.2-B's asynchronous job workflow](P1.2-PLAN.md) through the actual `creative-host-server.ts` process, opt-in local protocol **1.1.0**, the built-in render tools and Linux Remotion workers. The scenario creates a project and immutable snapshot over the wire, observes real frame progress, cancels work, verifies cleanup, produces new media, and queries exact persisted results after reopening. A second scenario kills its owned host during a live Chromium render and verifies explicit recovery without replay.

The historical protocol-1.0 AI trial and its 52-request replay remain unchanged. This deterministic engineering fixture makes no model calls and does not assess presentation quality. P1.1's two human-review items remain assigned to final acceptance.

## Interruption defect and fix

The first local run reproduced a concrete gap: after host `SIGKILL`, the guardian terminated and reaped the observed descendants, but the private `sciencemotion-worker-*` directory remained. Only the dead Node parent had previously removed it.

The guardian now removes its own per-job directory after draining descendants **when its original parent has disappeared**. It also removes that directory if the parent disappeared before guardian startup completed, without launching a renderer. A surviving parent still owns normal output verification and cleanup, so the guardian preserves its output file for that read. The parent relationship is checked with `getppid()`, not a stale PID liveness guess. A focused unit regression covers the startup case and preserves an unrelated sibling file; the real CLI crash scenario covers an active renderer.

This is cleanup by a surviving guardian. It does not cover a machine reboot, a killed guardian, host death before the guardian exists, or death after the guardian has handed output back and exited. Such cases still require operator inspection of the private temporary workspace. No process-tree CPU/RSS/disk quota is implied.

## Automated workflow and evidence

Run on Linux with Python 3, procfs, Node.js/tsx, Remotion's browser, FFmpeg and the existing fonts:

```bash
npm run typecheck
npm test
npm run accept:render-jobs
```

The platform suite contains **259 tests** at this increment (258 from B2 plus the guardian-startup regression). The separate CLI scenario checks:

1. Protocol-1.1 ready/capability negotiation, public project creation/snapshot saving and durable queued admission before completion.
2. Nonzero real video-frame progress with a live Chromium descendant. Cancel a queued job immediately and a running job through `stopping` to `cancelled`.
3. At terminal cancellation, every observed worker process is reaped, its temporary directory is gone, no Artifact or result was published, and project data is unchanged. Process checks retain PID plus start time and reject zombies too.
4. Identical submission retries do not create jobs. A new worker produces a PNG and 30-frame MP4. Verify content hashes, receipt/job/input/snapshot identity, local-process provenance, dimensions, frame rate and frame count; reopen and compare exact terminal records.
5. During another real render, capture the owned host/process/lock identities, kill only that spawned host, and wait for its observed tree to be reaped and its temporary directory removed. No interrupted Artifact appears.
6. A normal reopen fails while the exclusive locks remain. After the fixture's explicit verified-owner recovery, the abandoned `running` record becomes `interrupted`, with `interruptedFrom: "running"`, `outcomeUnknown: true`, retained input/progress and no result. Repeating the same submission returns that exact record without starting a worker or publishing output.
7. A deliberate new identity produces a 60-frame MP4. Reopen once more and compare all six jobs: two cancelled, three successful and one interrupted.

`out/render-job-cli/` contains `evidence.json`, session configurations, request/response traces, `after-cancel.png`, `after-cancel.mp4` and `after-recovery.mp4`. Evidence includes observed process identities, progress/stop/terminal records, verified lock identities, media receipts and cleanup timing. Traces contain temporary absolute paths from their run and are evidence, not portable launch configurations. CI uploads the directory as **`render-job-cli-evidence`**, including partial evidence on failure.

The outer Python acceptance harness is a subreaper that owns the test processes. It reaps the orphaned guardian after the deliberately killed host, including in containers whose PID 1 does not reap. Runtime guardians still perform renderer/Chromium cleanup themselves; the harness does not make a failed process-cleanup assertion pass by ignoring zombies. The harness has a five-minute deadline and cleans up its own children on failure.

## Explicit recovery boundary

There is no automatic lock takeover or general recovery command in B3. `host.lock` and `projects/writer.lock`, `executions/writer.lock`, `jobs/writer.lock` continue to protect the composed single-writer workspace. A PID written in a lock is diagnostic evidence, not sufficient proof that removing the lock is safe.

The fixture has stronger ownership evidence: it created a private directory, owns the exact spawned host, recorded each lock's device/inode/content while that host lived, observed its exit, and verified its process tree was reaped. It then verifies those same lock identities again, removes subordinate locks first and the root gate last, and explicitly starts a fresh host. Another startup attempt before this recovery must fail without altering the locks. These conditions are specific to this controlled fixture, not a stale-lock deletion recipe for arbitrary workspaces.

For an actual interrupted workspace, first stop all writers and automatic restarters under the operator's control, establish ownership and completion of descendant cleanup through the supervising service, and preserve job/execution/Artifact evidence. Only after exclusive ownership is established should the operator release confirmed abandoned locks and reopen. If ownership or publication is uncertain, keep the workspace closed for reconciliation. Do not delete ledgers or clear uncertainty merely to retry a render. Reopening preserves uncertainty and protects unresolved inputs; deliberate re-execution uses a new submission identity.

B1/B2 retain their tests of publication races and storage uncertainty. This real crash fixture interrupts **rendering before publication**; it does not claim physical power-loss testing or atomic transactions across the job ledger and Artifact store. C remains responsible for reconciliation/retention administration, independent queue/concurrency limits, fairness and concurrent editing/maintenance stress. D adds aggregate budgets; E measures performance. B is complete at this engineering boundary.
