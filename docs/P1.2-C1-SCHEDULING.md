# P1.2-C1 — Bounded concurrent job scheduling

Last updated: 2026-11-17

## Scope and position

C1 replaces B2's single background runner with independently bounded waiting and execution capacity and round-robin dispatch across waiting projects. It preserves immutable input admission, durable job records, authorization, cancellation/publication ordering and conservative interrupted recovery.

C is split into three increments: **C1 scheduling**, **C2 retention/reconciliation administration**, and **C3 actual concurrent editing/maintenance stress**. C1 does not complete C. The local protocol stays 1.1.0, the job API/schema stays 1.0.0, and the 19 built-in tools and historical protocol-1.0 replay remain unchanged.

## Trusted configuration

Use the same fields in native host options or the trusted local CLI config:

```json
{
  "schemaVersion": "1.0.0",
  "protocolVersion": "1.1.0",
  "directory": "workspace",
  "traceFile": "session.jsonl",
  "grant": {
    "projectId": "my-project",
    "permissions": ["snapshot.read", "artifact.write"],
    "toolIds": ["render.preview", "render.video"]
  },
  "renderJobs": { "maxConcurrentJobs": 2, "maxQueuedJobs": 6, "timeoutMs": 30000 },
  "renderWorker": { "maxConcurrentJobs": 2 }
}
```

This grant renders already-retained snapshots; creation/editing needs the corresponding explicit grants.

| Setting | Default | Contract |
| --- | --- | --- |
| maxConcurrentJobs | 1 | 1–4 reserved execution slots |
| maxQueuedJobs | 7 | 0–31 waiting jobs; running plus waiting capacity must be at most 32 |
| timeoutMs | 30,000 | 1–300,000 ms, capped by existing host/tool limits; begins on claim, not during queue waiting |
| maxActiveJobs | Legacy input only | 1–32 maps to one execution slot and N−1 waiting slots; cannot be mixed with either new count |

A zero-sized waiting queue still admits a job when an execution slot is free. At saturation, new work fails with HOST_JOB_CAPACITY before persisting a new identity; callers may retry later. Identical submissions return their existing record without creating work. Pending distinct admission requests have a separate bound equal to execution plus waiting capacity; identical in-flight requests share one admission.

The existing worker adapter has its own maxConcurrentJobs ceiling. Configure it at least as high as background concurrency; an incompatible combination fails before acquiring the workspace lock. The in-process default and trusted injected renderers support the scheduler interface but remain cooperative during cancellation. Native background scheduling does not reserve capacity against legacy synchronous render/layout calls: they still use their original service queue and share the selected worker adapter. Competing synchronous work can cause the adapter's explicit RENDER_WORKER_BUSY rejection. This increment does not claim a unified quota or fairness across those two APIs.

## Dispatch and lifecycle

Each waiting project owns a FIFO. At each available execution slot, take one job from the next project, then move that project's remaining queue to the end of the rotation. Fairness applies among already-admitted waiting projects, with no preemption or duration-weighted guarantee. The global admission bound does not reserve space for projects that arrive after the queue is full. Completion order may differ from dispatch order with multiple executors.

Execution slots are reserved synchronously at dispatch and remain occupied through claim, rendering, real process/file cleanup and serialized result publication. The initial durable acknowledgement remains a queued record; a slot-reserved job can briefly still appear queued while claim is persisted. maxQueuedJobs counts waiting work, excluding those reserved slots.

Cancelling waiting work removes it from its project queue and frees waiting capacity. A running stop keeps its execution slot until the renderer actually settles; a non-cooperative renderer cannot make a free slot merely by acknowledging a stop. A committed publication refuses cancellation and retains its slot until publication finishes.

Plugin activation stops new admission and drains every executor and waiting job before switching. Host close cancels waiting and running work, waits for all active executors and committed publications, then releases resources. A fatal storage/cleanup failure stops dispatch and aborts sibling renderers; a sibling returning after that failure cannot begin publication. Drain still waits for every actual executor, even if one has already failed. Uncommitted active records remain unresolved for conservative recovery; committed publication keeps the existing uncertainty boundary.

At C1, snapshot pins and output references retained B2 semantics. C2 adds explicit reconciliation and release administration on top of the scheduler. [C2 retention](P1.2-C2-RETENTION.md).

## Verification

Ten scheduler regressions cover configuration/legacy compatibility, worker-capacity mismatch, simultaneous execution with queue saturation, queued/running cancellation, zero waiting capacity, three-project round-robin/FIFO order, session revocation, host close, plugin drain, sibling cleanup failure, committed publication and independent execution deadlines. They use controlled renderer settlement so a stop acknowledgement cannot masquerade as actual cleanup.

```bash
npm run typecheck
npm test
npm run accept:render-scheduler
```

The platform suite is 269 tests at this increment. The separate real-worker scenario creates two projects and snapshots through public tools, submits two videos plus one queued preview, rejects overflow without a new identity, and observes two live guardian/Chromium trees at once. It verifies a peak of two workers, delayed dispatch of waiting work, two 640×360 / 30 FPS / 180-frame MP4s and a PNG, byte/input/snapshot receipts, observed process reaping, private temporary-directory cleanup and exact terminal records after reopening. It makes no model calls and is not a human presentation review.

CI uploads out/render-job-scheduler/ as **render-scheduler-evidence**, including partial evidence on failure. It contains evidence.json, worker events, concurrent process observations, receipts and a.mp4, b.mp4, queued-preview.png. Existing B3 CLI interruption/cancellation, historical AI/worker replay, two-topic restoration and media/audio regressions continue independently.

C3 must still demonstrate editing a project and saving a newer snapshot while its older snapshot renders, retention/GC stress, and lifecycle operations under sustained queue pressure. D remains responsible for enforced aggregate process-tree CPU/RSS/temporary-disk budgets; E measures performance. C1's concurrent process observation is not a resource quota or throughput benchmark.
