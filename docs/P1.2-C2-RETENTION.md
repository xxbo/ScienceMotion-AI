# P1.2-C2 — Render job retention and reconciliation

Last updated 2026-11-18

C2 adds application-only administration under `host.maintenance.renderJobs`. Project-bound AI sessions and stdio 1.1 use the same four job methods and job record shape. Maintenance runs through the same serialized host queue as admission, publication, snapshot release and garbage collection. Background rendering continues outside that queue.

## Maintenance API

| Method | Behavior |
| --- | --- |
| `inspect(projectId, jobId)` | Return the execution record, matching retained snapshot and its local Artifact IDs, whether the job blocks snapshot release, output identity and verification, and persisted maintenance evidence. Return the compact record for a pruned job or `undefined` for a missing or foreign job. |
| `reconcile(projectId, jobId, decision)` | Record an explicit disposition for an interrupted job or a failure with uncertain publication. `{ action: "discard", reason }` resolves the retention decision without adopting an output. `{ action: "retain-output", reason, artifactId? }` verifies an output bound to the job and attaches a reference owned by that job. Reasons are 1–512 UTF-8 bytes. |
| `release(projectId, jobId)` | Persist release intent for a resolved terminal job, detach its output references, then persist completion. The workspace snapshot has its own lifecycle. Call `host.maintenance.releaseSnapshot` to release it once every job pin has cleared. |
| `prune(projectId, jobId)` | Compact a record after release is complete. Preserve the job and submission identities, hashes, reconciliation decision and release dates in the ledger. This frees a detailed-record slot. Compact records still count toward the ledger byte limit. |

Repeat a decision, release or prune to retrieve the already persisted result. A conflicting decision returns `RENDER_JOB_RECONCILIATION_CONFLICT`. The original execution record retains its state, diagnostics and uncertainty fields. An exact retry of a pruned submission returns `RENDER_JOB_PRUNED`, and changed parameters under that identity return `RENDER_JOB_CONFLICT`. A new render uses a new submission identity.

## Publication and cleanup

The durable publication barrier now records the candidate's content hash, byte size, media type and job identity before the first Artifact write. GC protects that identity until release completes, including after a failure between writing the bytes and attaching their reference. `inspect` reports availability as `verified`, `missing` or `unverified`. A candidate is eligible for adoption only after its stored metadata and bytes match the receipt.

Each new job owns its own output reference. Identical bytes remain eligible for use by other jobs, projects, snapshots and synchronous invocations. Releasing one job drops only its references. `collectGarbage` applies its normal age and reference checks to the Artifact after release completes. A failed detach or a lost acknowledgement leaves an inspectable release intent. Repeating `release` preserves the original intent timestamp and syncs the reference directory before completing, even when the prior attempt already removed the reference.

Active jobs and unresolved interrupted or uncertain jobs pin their input snapshots and dependencies. A persisted reconciliation allows explicit snapshot release when no other job pins it. An independently retained snapshot continues to protect its inputs.

The ledger opens pre-C2 records. Their outputs can have shared `tool-run` references keyed by project, run and call. Inspection reports a matching legacy reference when its Artifact is identified. Job release preserves these shared references. Old uncertain publications without an output identity block GC until an operator reconciles them. To retain an older output, supply its Artifact ID. The original publisher metadata and provenance must bind it to the exact job and input hash, and the stored bytes must verify. Where that evidence is unavailable, an operator can record a discard disposition after reviewing the workspace evidence. Use the [B3 verified-owner procedure](P1.2-B3-CLI-LIFECYCLE.md) for an abandoned workspace before reopening it.

## Verification

The platform tests exercise candidate protection without an attached reference, rejection of corrupt or foreign evidence, explicit adoption and discard, released-reference isolation for shared bytes, restart during release, legacy compatibility, and checksummed compaction. The real `npm run render:job-smoke` scenario renders PNG and MP4 through the production host, reopens the workspace, reclaims the released PNG while preserving the MP4, compacts the PNG job and checks its identity after another reopen. CI includes `out/job-host-evidence.json` and both exported media files in `sciencemotion-demo`.

C3 exercises retention and release while a real render and a project edit overlap under queue pressure. [C3 concurrent maintenance](P1.2-C3-CONCURRENT-MAINTENANCE.md).
