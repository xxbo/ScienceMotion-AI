# P1.2-C3 — Concurrent editing and maintenance acceptance

Last updated 2026-11-18

C3 exercises the production Creative Host and disposable Linux render workers with one execution slot and one waiting slot. Two projects use independent snapshots and visibly different charts. The fixture uses the existing typed project tools, background job APIs and trusted maintenance operations.

## Acceptance scenario

1. Save snapshot S with a chart and a content-addressed source asset. Start a video of S and observe frame progress and a live Chromium process tree. Use the public revisioned patch tool to swap the two chart values, change the fill and remove the old source from the project head. Save the edited revision as S2 while S is still rendering. The chart keeps its materialized rows in Project Graph and declares the original source asset in S.
2. Verify project isolation by denying a foreign snapshot submission and job cancellation, and by comparing the second project's head. Queue a preview of S2 and reject a third job at capacity. With S rendering and S2 waiting, maintenance must reject release of S. GC collects an unrelated control artifact and preserves the source held by S.
3. Activate a second version of the acceptance plugin under the same queue pressure. The host rejects new submissions and maintenance during switching. The candidate's health check observes both original jobs durably succeeded with receipts. The existing session discovers the new version after activation.
4. Verify the first and final frames of the 360-frame H.264 video still show S's original chart. The S2 PNG shows the swapped bars, and the other project's PNG has its own chart color and snapshot receipt. The previously rejected third submission succeeds once capacity opens. After explicit job and snapshot release, GC collects S's output and its source while preserving the two other renders.
5. Start another real video worker, fill the waiting slot and close the host. Check that it rejects later admission, cancels both jobs, reaps the observed Chromium tree and empties the private temporary directory. Reopen with the selected plugin factory and verify the project heads, unchanged success records, released snapshot and recorded cancellations. The waiting job has no start timestamp and neither cancelled job publishes an Artifact.

## Run and evidence

```bash
npm run typecheck
npm run accept:render-maintenance
```

The scenario uses Linux, Python 3, the Remotion browser, FFmpeg and ffprobe. It writes `out/render-job-maintenance/`. CI uploads this directory as `render-maintenance-evidence`, including partial evidence on failure. On success it contains `evidence.json`, `snapshot-s.mp4`, `snapshot-s2.png` and `other-project.png`. The JSON records snapshot and byte receipts, decoded chart pixels, live worker observations, queue rejections, GC results and reopened job records.

C1 retains separate evidence of two simultaneous render workers. B3 covers abrupt host interruption and verified-owner lock recovery. D is the next increment and addresses aggregate CPU, memory and temporary-disk budgets for the worker tree. Human presentation review stays with final acceptance.
