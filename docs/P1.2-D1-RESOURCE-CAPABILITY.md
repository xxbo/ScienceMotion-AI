# P1.2-D1 — Render resource budgets and host capability

Last updated 2026-11-18

D1 defines a trusted per-job budget for the Node renderer and its descendants, including Chromium and FFmpeg. The host and the Python guardian stay outside the job's resource group so they can record failures and finish cleanup. The operator selects the budget in `renderWorker.resourceBudget` on the embedding API or in the trusted stdio launch configuration.

## Budget contract

| Field | Unit and scope |
| --- | --- |
| `cpuMillicores` | Thousandths of one CPU core across the job tree. Use `cpu.max` with a 100 ms period. Linux's 1 ms minimum quota makes the minimum 10 millicores. Bandwidth exhaustion throttles the group. |
| `cpuTimeMs` | Cumulative CPU milliseconds across the job tree. Use the `cpu.stat` counter `usage_usec`. D2 will record the sampling and termination behavior when exhaustion triggers a failed job. |
| `memoryBytes` | Bytes charged by the cgroup memory controller. `memory.max` applies to the group, including the memory of its descendants and charged page cache. The kernel accounts memory by page. D2 will verify the OOM counters and cleanup. |
| `temporaryBytes` | Upper capacity of the job's dedicated temporary filesystem in bytes. Filesystem metadata also consumes capacity. D3 puts the worker's files, browser profile and render intermediates within the job volume. |

Supply at least one field. Values are positive safe integers, with the CPU conversion bounds checked before multiplying into microseconds. D1 introduced the startup failure `RENDER_WORKER_RESOURCE_UNAVAILABLE`. D2 enables CPU and memory budgets on a delegated cgroup v2 parent. Invalid values return `RENDER_WORKER_CONFIG`. Leave `resourceBudget` omitted to use the worker lifecycle and existing limits. [D2 configuration](P1.2-D2-CPU-MEMORY.md) · [Worker lifecycle](P1.2-WORKERS.md).

## Capability evidence

```bash
npm run --silent probe:render-resources
```

The default command reports cgroup v2 and controller visibility, whether the current process can write the standard root's controller file, and which active checks were run. It reports `enforcement: "probe-only"`. For example, the current development container exposes the `cpu` and `memory` controllers and restricts root-level controller writes for its ordinary user.

On a Linux test machine, supply two operator-prepared paths for active verification. `--require` exits unsuccessfully if either check is unavailable or untested and still emits the report.

```bash
npm run --silent probe:render-resources -- \
  --cgroup-parent /path/to/delegated-cgroup \
  --temporary-volume /path/to/disposable-ext4-loop-mount \
  --require
```

- The cgroup parent needs `cpu` and `memory` enabled for children. The probe creates one child, writes and reads back the two controls, moves its own short-lived test process, reads the CPU and memory counters, and removes the test cgroup.
- The storage path must be the root of an empty, dedicated ext4 loop mount of at most 64 MiB. The probe writes an owned file until the kernel returns `ENOSPC`, deletes the file and checks that the space is reclaimed.

The `probe-render-resources` job in Video Engine CI uses a GitHub-hosted Ubuntu 24.04 runner. It prepares a 32 MiB file-backed ext4 volume and runs the probe as the ordinary runner user inside a service with delegated CPU and memory controllers. The service puts the probe in a manager leaf so that the parent can enable controllers for worker children. CI uploads the report as `render-resource-capability`. This is the selected acceptance environment for D2 and D3. [CI configuration](../.github/workflows/video-engine.yml) · [systemd delegation](https://www.freedesktop.org/software/systemd/man/latest/systemd.resource-control.html).

D2 connects the cgroup controls to the worker lifecycle. D3 verifies storage capacity and cleanup in the worker and its subprocesses. D4 will exercise all three budgets with real renders and verify parallel isolation and admission recovery.
