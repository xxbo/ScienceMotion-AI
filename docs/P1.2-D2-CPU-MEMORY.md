# P1.2-D2 — Render worker CPU and memory

Set `renderWorker.cgroupParent` and `renderWorker.resourceBudget` in the trusted host options or local stdio launch configuration. Set any combination of `cpuMillicores`, `cpuTimeMs` and `memoryBytes`. A host without a resource budget uses the existing worker lifecycle and limits. [Budget units](P1.2-D1-RESOURCE-CAPABILITY.md).

```json
{
  "renderWorker": {
    "cgroupParent": "/sys/fs/cgroup/system.slice/sciencemotion.service",
    "resourceBudget": {
      "cpuMillicores": 1500,
      "cpuTimeMs": 15000,
      "memoryBytes": 1610612736
    }
  }
}
```

The supplied directory must be on cgroup v2 and delegated to the host user. Enable `cpu` for bandwidth and `memory` for memory limits. Place the host in a manager leaf so the delegated parent can distribute domain controllers to job children. The startup check creates a disposable cgroup, exercises the requested controls and process migration, and checks `cgroup.kill`. Unavailable enforcement returns `RENDER_WORKER_RESOURCE_UNAVAILABLE` before opening the workspace or starting a renderer. The guardian checks the selected controls again for each job. An enabled `temporaryBytes` budget still returns `RENDER_WORKER_RESOURCE_UNAVAILABLE` until D3. [Linux cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html).

| Control | Enforcement and evidence |
| --- | --- |
| CPU bandwidth | `cpu.max` applies a 100 ms period and a quota of `cpuMillicores × 100` microseconds across the tree. The kernel throttles runnable work when the period's quota is used. The final `cpuThrottledPeriods` counter records throttling. |
| Cumulative CPU | The guardian samples `cpu.stat` during the job and again after reaping. At or above `cpuTimeMs`, it returns `RENDER_WORKER_CPU_TIME_LIMIT` with the measured usage. The polling interval and scheduling/cleanup latency allow some overshoot. |
| Charged memory | `memory.max` sets the page-accounted limit, including charged page cache. `memory.swap.max=0` disables swap for the job and `memory.oom.group=1` requests group OOM handling. OOM events or an OOM kill charged to the group produce `RENDER_WORKER_MEMORY_LIMIT`. |

The guardian migrates the blocked child before Node starts, so its Chromium and FFmpeg descendants inherit the job cgroup. The host and guardian stay in the manager group. The guardian terminates and reaps owned processes, samples final counters and removes the cgroup before the host releases the worker slot or publishes a verified result. Unexpected counter failures use `RENDER_WORKER_RESOURCE_ACCOUNTING`. If cleanup cannot be verified, the host uses `RENDER_WORKER_CLEANUP` and the job runner applies its existing conservative recovery path. Background resource exhaustion persists as a failed job with a diagnostic and no output receipt. Final worker events and successful render execution metadata include decimal-string `resourceUsage` counters for the enabled controls.

## Acceptance evidence

Video Engine CI runs the acceptance script as an ordinary user in a delegated Ubuntu 24.04 service. A detached CPU workload triggers both throttling and cumulative exhaustion. A detached memory workload triggers a kernel OOM. The fixture checks membership, failure diagnostics, process and directory cleanup, slot reuse, and exact records after reopening the host. The production worker renders a 180-frame MP4 with Chromium and FFmpeg observed inside the same budgeted cgroup. CI uploads the MP4 and JSON evidence as `render-worker-resource-evidence`. [CI workflow](../.github/workflows/video-engine.yml) · [Acceptance script](../scripts/render-worker-resource-acceptance.ts).
