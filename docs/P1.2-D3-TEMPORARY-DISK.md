# P1.2-D3 — Render worker temporary disk

Set `renderWorker.resourceBudget.temporaryBytes` and `renderWorker.temporaryVolumes` in the trusted host options or local stdio launch configuration. Supply a distinct ext4 loop mount root for each concurrent worker slot. The image backing each loop device must fit within `temporaryBytes`. Ext4 metadata consumes some of that capacity. CPU and memory controls use the same resource policy with a delegated cgroup parent. [D2 configuration](P1.2-D2-CPU-MEMORY.md).

```json
{
  "renderWorker": {
    "maxConcurrentJobs": 1,
    "temporaryVolumes": ["/srv/sciencemotion/slot-1"],
    "resourceBudget": { "temporaryBytes": 134217728 }
  }
}
```

Provision the loop filesystems before starting the host. The Ubuntu fixture preallocates each backing image, formats it as ext4 and mounts it with `nosuid,nodev,noexec`. Mount roots must be writable by the worker user, owned by that user and dedicated to the worker pool. An idle root contains only ext4's optional `lost+found`. Startup verifies the actual mount, loop device size, exclusive access and write/cleanup behavior. Missing, undersized policy capacity, dirty or unavailable storage returns `RENDER_WORKER_RESOURCE_UNAVAILABLE` before opening the workspace. Install the Remotion browser before serving jobs. [Ubuntu bootstrapping fixture](../scripts/fixtures/render-volume-ci.sh).

A guardian leases a mount exclusively before starting Node and creates a private working directory inside it. It puts the renderer's request, temporary files, cache and profile directories, bundle, encoding intermediates and result file on that filesystem. Budgeted rendering uses a fresh bundle and the installed browser. Chromium's profile and FFmpeg's output paths inherit the job directory. The host keeps its bounded request and verified output handoff in its own private directory and publishes Artifacts after the guardian exits.

Ext4 enforces capacity during file creation and writes. The renderer preserves disk exhaustion reported by Node or its render tools. The guardian also samples free blocks and inodes and stops work that continues after the volume fills. Background jobs record `RENDER_WORKER_TEMPORARY_LIMIT` as a failed job with no result. The guardian terminates and reaps the process tree, verifies that blocks and inodes were reclaimed, and releases the lease. The mounted slot can then serve another job. Uncertain cleanup returns `RENDER_WORKER_CLEANUP`, which uses the existing conservative job recovery path.

Final worker events and successful rendering receipts include decimal-string `temporaryCapacityBytes`, `temporaryMinimumAvailableBytes` and `temporaryMinimumAvailableInodes`. The minimum values are samples taken during execution and after reaping. The kernel applies the filesystem capacity throughout the job. [Resource contract](P1.2-D1-RESOURCE-CAPABILITY.md).

## Acceptance evidence

The Video Engine CI resource job provisions a 128 MiB loop filesystem on Ubuntu 24.04. A detached writer receives real `ENOSPC`, an overlapping lease attempt is refused, and the failed job survives host reopening. The same worker accepts another job after its slot and filesystem blocks are reclaimed. A production render captures Chromium's profile, the bundle, intermediates and an FFmpeg output path inside the volume. CI saves the 180-frame MP4 and evidence as `render-worker-temporary-evidence`. [CI workflow](../.github/workflows/video-engine.yml) · [Acceptance script](../scripts/render-worker-temporary-acceptance.ts).

With dependencies and the Remotion browser installed, run the same acceptance on the Ubuntu runner or an equivalent Linux host with permission to provision loop devices.

```sh
bash scripts/fixtures/accept-render-temporary-ci.sh
```
