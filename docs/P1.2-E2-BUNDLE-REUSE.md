# P1.2-E2 — Prepared render bundle reuse

E1 measured a 3.66-second median bundling stage on repeat previews from disposable workers. A prepared Remotion bundle amortizes compilation across jobs. The worker validates and stages a private copy before each render. The worker guardian owns the whole job from setup through process and temporary-file cleanup. [E1 baseline](P1.2-E1-PERFORMANCE-BASELINE.md) · [E1 measurements](https://github.com/xxbo/ScienceMotion-AI/actions/runs/44454590531/artifacts/14497630844).

## Prepare and select a bundle

Run the build in the target runtime, with the application's render code and public assets installed. Choose a new output directory for each deployment.

```sh
npm run --silent prepare:render-bundle -- --output out/renderer-v1
```

The command prints a JSON object containing the absolute `directory` and its `sha256` identity. Supply the object as `renderWorker.preparedBundle` in `openCreativeHost` or the trusted stdio launch configuration. The `--entry-point` option selects an alternative entry point during preparation. The operator owns installation and retention of these directories. Select the new object after preparing an updated deployment.

The identity covers the emitted code and asset tree, platform, architecture, Node.js version, and the installed Remotion, bundler and renderer versions. A worker verifies the bytes it will serve before opening Chromium. Missing, changed, unsupported or oversized input produces `RENDER_WORKER_BUNDLE_INVALID`. The bundle must consist of local regular files and directories. Each staged copy is limited to 128 MiB of file data and 4,096 entries. Disk-budgeted workers stage it on their leased volume. Snapshot data, browser state and rendered output stay scoped to each job. [Worker contract](P1.2-WORKERS.md).

## Measure the trade-off

```sh
npm run bench:render -- --compare bundle --samples 3
```

The paired comparison uses E1's immutable snapshot, operation order and output checks. Both arms start with a fresh host and workspace and use a new disposable worker for each call. In the prepared arm, one clean build runs before the first request. Its time is reported separately and counted in the whole sample. The bundle stage of each request includes verification and copying. The temporary-space peak includes both the prepared tree and its staged copy. CPU and RSS include bundle preparation.

One local pair on Debian 13 with Node 24 took 4.63 seconds for an ordinary repeat preview and 1.65 seconds with a prepared bundle. Preparation took 12.50 seconds. The whole workload took 46.83 and 26.16 seconds respectively. The prepared path used 0.66 seconds from the repeat request to its first bundle event, which frames the potential gain from retaining the Node worker. A resident worker would need per-job resource accounting and an equivalent cleanup guarantee for every owned process. E2 adopts bundle reuse with disposable workers.

CI publishes three paired repetitions in `render-bundle-reuse` with raw measurements, medians and ranges, alongside the original `render-performance-baseline`. The `acceptance.json` report covers parallel previews of different snapshots, content and runtime invalidation, rejection of symlinks and oversized input, cancellation during the bundle stage, and exact recovery output. The temporary-disk acceptance also verifies staging on a real ext4 lease and reclaiming its blocks and inodes after rendering.
