# P1.2 — Local execution and job management

Last updated: 2026-11-17

## Goal and current position

Let an AI client submit a bounded render, receive a job identity, inspect progress and request cancellation while the host remains responsive. Persist enough evidence to distinguish completed, cancelled and interrupted work after reopening. Keep Project Graph snapshots, tool grants and Artifact publication as the existing sources of truth.

**A is delivered on main; B is the next implementation step.** This document defines B–E and their delivery criteria; it does not claim those APIs or guarantees already exist. Steps differ in size, so one completed step out of five is not an effort percentage.

The user explicitly deferred human effect review to a final acceptance workstream. P1.1's two human-review items stay open there and do not block P1.2 development. Automated tests, real-render regression and PR/main CI remain required for every engineering increment.

## A — Delivered baseline

[PR #8](https://github.com/xxbo/ScienceMotion-AI/pull/8) delivered main `b4e5bc9fa47111ce8a8324f69b14559d25d4f1de`; [main CI #44002989900](https://github.com/xxbo/ScienceMotion-AI/actions/runs/44002989900) passed all 223 platform tests and the real-render regressions. The [worker implementation notes](P1.2-WORKERS.md) define the exact boundary.

Existing capabilities include a Linux subreaper guardian, cancellation/deadline handling through temporary cleanup, bounded admission/output and V8 old-space, application progress callbacks, and per-render process receipts. The CLI can opt into worker execution. The host's render tools and request dispatch are still synchronous; job submission/query/cancellation endpoints do not exist yet. Whole-process-tree CPU/RSS/disk budgets and background editing are not delivered by A.

## B — Next implementation: durable asynchronous jobs

Deliver B in reviewable increments, preserving the existing synchronous tools and historical AI replay:

1. **B1: job contract and durable ledger.** Define project-scoped job identity, immutable snapshot ID/hash/revision, render operation/parameters, input hash, timestamps, bounded progress, diagnostics and result receipt. Specify legal transitions and persistence before acknowledging admission. A repeated submission identity with the same request returns the original job; different input under that identity fails explicitly. This foundation alone does not complete B.
2. **B2: host and local-client integration.** Expose submit, get/list and cancel operations through the project's existing authorization boundary. Exact method/tool names and schema versions must be committed with implementation and tests. Return a job ID before the render finishes; status and cancellation must not wait behind that render. Preserve tool/version grants, project ownership and bounded request/output rules. Revoke/close behavior must be explicit and tested.
3. **B3: real execution, durable outcomes and restart evidence.** Connect the APIs to A's real worker, retain progress and cancellation evidence, bind successful Artifacts to the job/snapshot, and test reopen/interruption behavior. Complete one actual CLI workflow: submit → observe progress → cancel → verify cleanup/no cancelled result → submit again → inspect successful output → reopen and query the persisted result.

The state design must distinguish waiting, running, cancellation requested, success, failure, timeout, cancellation completed and interruption. A cancellation acknowledgement is not evidence that the worker has exited; a terminal cancelled state requires actual cleanup. Progress is bounded and throttled rather than synchronously persisted for every frame.

Before returning a submission receipt, validate and retain its immutable input identity and required dependencies. Do not defer this minimum protection to C: a pending job must never silently render different content under a reused snapshot ID. C expands scheduling and proves retention under concurrent editing/maintenance.

Persist admission before execution and terminal success only after output verification/publication. If the host stops between publication and terminal evidence, expose an interrupted/uncertain result with reconciliation information; do not claim rollback or automatically replay effects. Reopening must respect existing exclusive-writer locks and an explicit recovery procedure, with no blind stale-lock deletion. Automatic resume/retry is not required for B's first delivery.

B must test cross-project access, restricted/revoked grants, duplicate/conflicting submissions, queued/running cancellation, late success, timeouts, publication failure/uncertainty and restart evidence. Keep the independent tool-execution ledger and job ledger responsibilities explicit. A persisted job is not itself a new creative document or a second project model.

## C — Scheduling and concurrent work

Move long renderer execution outside the canonical project write queue while retaining short serialized admission/publication operations. Bound waiting jobs and running workers independently; define overload behavior, ordering, per-project fairness and cancellation of queued work. Start with a local single-host scheduler.

Demonstrate a running render of snapshot S while the same project is edited and a newer snapshot is saved. The old job must still produce S's result. Reject premature release/GC of retained inputs, then release job-owned references after the documented terminal/reconciliation boundary. Test host close, plugin transitions and queue saturation without losing ownership or admitting unbounded work.

## D — Aggregate resource control

Measure and enforce budgets across Node, Chromium, FFmpeg and other owned descendants on the supported Linux runtime. State which controls are available and enforced; a V8 heap flag, output-size cap or observed RSS sample is not an aggregate memory/CPU/disk guarantee. Unsupported enforcement must be explicit.

Exercise CPU exhaustion, memory pressure and temporary-file growth with bounded fixtures. Exceeding a configured budget must produce a typed failure, terminate/reap owned work, recover capacity and permit another job. Third-party code sandboxing and remote execution remain outside this local milestone.

## E — Performance evidence and justified reuse

Measure cold startup/bundling, preview/video/layout execution, cancellation latency, cleanup time and process-tree resource usage on the same representative inputs and recorded environment. Compare default in-process and disposable-worker paths without weakening their correctness checks.

Use those measurements to decide whether bundle caching or worker reuse is worthwhile. If reuse is introduced, key it by code/assets/render environment and prove invalidation, bounded resource retention and absence of state leakage between projects. Retaining disposable workers with a documented measurement-based decision is valid; reuse is not mandatory.

## Delivery and final acceptance

For every implemented increment: meaningful tests and real-render evidence where behavior changes, full PR CI, prompt merge, verification of main push CI, and updated status/evidence links. A–E are engineering milestones; their CI does not close human presentation review.

The [final acceptance workstream](PLAN.md#final-human-acceptance-workstream) collects P1.1's two-fixture review and representative outputs from later work. It reviews approved content, legibility, clipping/overlap, motion and narration/caption alignment where present, records issues and their fixes, and identifies the final main commit and reviewed outputs. The user has scheduled this work for the end; no human-review approval is required to begin B.
