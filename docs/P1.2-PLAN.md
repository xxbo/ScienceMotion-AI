# P1.2 — Local execution and job management

Last updated 2026-11-18

## Goal and current position

Let an AI client submit a bounded render, receive a job identity, inspect progress and request cancellation while the host remains responsive. Persist enough evidence to distinguish completed, cancelled and interrupted work after reopening. Keep Project Graph snapshots, tool grants and Artifact publication as the existing sources of truth.

**A, B (B1–B3), C (C1–C3), D1 and D2 are implemented. D3 is next.** C1 supplies independent waiting/execution limits, configurable concurrency and per-project round-robin dispatch. C2 adds trusted retention inspection, explicit reconciliation, release and pruning. C3 exercises the combined behavior with real workers during project edits, maintenance and queue saturation. D2 enforces per-job CPU and memory budgets with Linux cgroup v2. [B3 lifecycle](P1.2-B3-CLI-LIFECYCLE.md) · [C1 scheduling](P1.2-C1-SCHEDULING.md) · [C2 retention](P1.2-C2-RETENTION.md) · [C3 concurrent maintenance](P1.2-C3-CONCURRENT-MAINTENANCE.md) · [D1 resource capability](P1.2-D1-RESOURCE-CAPABILITY.md) · [D2 CPU and memory](P1.2-D2-CPU-MEMORY.md).

The user explicitly deferred human effect review to a final acceptance workstream. P1.1's two human-review items stay open there and do not block P1.2 development. Automated tests, real-render regression and PR/main CI remain required for every engineering increment.

## B — Durable asynchronous jobs

Deliver B in reviewable increments, preserving the existing synchronous tools and historical AI replay:

1. **B1 — implemented: job contract and durable ledger.** [Contract and persistence evidence](P1.2-B1-JOB-LEDGER.md) cover project-scoped submission identity, immutable input hash, owned transitions, throttled progress, publication/stop races, bounded receipts, synced atomic writes and conservative interruption on reopen. Eighteen focused tests include process abandonment and filesystem failure/corruption. This is an internal store; it does not authorize/pin inputs, launch workers or expose a client API, and does not complete B.
2. **B2 — implemented: host and local-client integration.** [Job API 1.0.0 and opt-in local protocol 1.1.0](P1.2-B2-HOST-JOBS.md) expose `jobs.submit/get/list/cancel`, preserving grants, exact versions, project ownership and request/output bounds. A bounded single runner performs long rendering outside the project queue, with retained input admission, coalesced progress and verified result publication. Seventeen tests cover session/host/stream integration, revoke/close/plugin drain, races, retention/GC and failures. A real PNG/MP4 host-API smoke verifies output receipts and exact persisted results after reopen. Historical protocol 1.0 and its 19 tools are unchanged.
3. **B3 — implemented: real worker/CLI cancellation and interrupted-host evidence.** [CLI lifecycle and recovery evidence](P1.2-B3-CLI-LIFECYCLE.md) exercise the host-selected A worker through protocol 1.1: submit → observe real progress → cancel → verify process/temp cleanup and no cancelled result → submit again → verify PNG/MP4 → reopen and query exact results. The fixture also kills its owned host during rendering, verifies cleanup and exclusive-lock refusal, performs explicit verified-owner recovery, and queries interrupted/uncertain evidence without replay. A reproduced temporary-directory leak after parent death is fixed in the guardian, with startup and real-render regressions.

B1 distinguishes `queued`, `running`, `stopping`, `publishing`, `succeeded`, `failed`, `cancelled`, `timed-out` and `interrupted`. A stop-request acknowledgement is not evidence that the worker has exited. B2 waits for renderer settlement before terminal cancellation and verifies/retains output before success; B3 proves the real process/CLI interruption path. The durable publication barrier rejects later stop requests explicitly. Progress is coalesced and throttled rather than synchronously persisted for every frame.

Before returning a **client-facing** submission receipt, B2 authorizes the operation, validates the snapshot and local dependencies, and durably pins its retained identity through the job ledger. B1's internal `store.submit` alone still persists metadata only. Active jobs and unresolved interrupted or uncertain jobs block snapshot release. [C2 retention](P1.2-C2-RETENTION.md).

Persist admission before execution and terminal success only after output verification/publication. If the host stops between publication and terminal evidence, expose an interrupted/uncertain result with reconciliation information; do not claim rollback or automatically replay effects. Reopening must respect existing exclusive-writer locks and an explicit recovery procedure, with no blind stale-lock deletion. Automatic resume/retry is not required for B's first delivery.

B must test cross-project access, restricted/revoked grants, duplicate/conflicting submissions, queued/running cancellation, late success, timeouts, publication failure/uncertainty and restart evidence. Keep the independent tool-execution ledger and job ledger responsibilities explicit. A persisted job is not itself a new creative document or a second project model.

## D — Aggregate resource control

Measure and enforce budgets across Node, Chromium, FFmpeg and other owned descendants on the supported Linux runtime. State which controls are available and enforced; a V8 heap flag, output-size cap or observed RSS sample is not an aggregate memory/CPU/disk guarantee. Unsupported enforcement must be explicit.

| Increment | Status | Acceptance evidence |
| --- | --- | --- |
| D1 — Capability and budget contract | Implemented | Trusted policy validates units and rejects unavailable enforcement before startup. Ubuntu CI verifies CPU and memory delegation and a bounded disk-backed filesystem. [D1 capability](P1.2-D1-RESOURCE-CAPABILITY.md) |
| D2 — CPU and memory | Implemented | Per-job cgroup membership before renderer execution, kernel CPU throttling and cumulative accounting, memory OOM, typed failures, guardian cleanup and a budgeted MP4. [D2 evidence](P1.2-D2-CPU-MEMORY.md) |
| D3 — Temporary disk | Next | Per-job capacity covers worker, browser and render intermediates. File growth hits a kernel limit and cleanup reclaims the volume. |
| D4 — Combined real-worker acceptance | Pending | CPU, memory and disk exhaustion produce distinct durable failures. Parallel healthy work succeeds and released slots accept new jobs. |

Exercise CPU exhaustion, memory pressure and temporary-file growth with bounded fixtures. Exceeding a configured budget must produce a typed failure, terminate/reap owned work, recover capacity and permit another job. Third-party code sandboxing and remote execution remain outside this local milestone.

## E — Performance evidence and justified reuse

Measure cold startup/bundling, preview/video/layout execution, cancellation latency, cleanup time and process-tree resource usage on the same representative inputs and recorded environment. Compare default in-process and disposable-worker paths without weakening their correctness checks.

Use those measurements to decide whether bundle caching or worker reuse is worthwhile. If reuse is introduced, key it by code/assets/render environment and prove invalidation, bounded resource retention and absence of state leakage between projects. Retaining disposable workers with a documented measurement-based decision is valid; reuse is not mandatory.

## Delivery and final acceptance

For every implemented increment: meaningful tests and real-render evidence where behavior changes, full PR CI, prompt merge, verification of main push CI, and updated status/evidence links. A–E are engineering milestones; their CI does not close human presentation review.

The [final acceptance workstream](PLAN.md#final-human-acceptance-workstream) collects P1.1's two-fixture review and representative outputs from later work. It reviews approved content, legibility, clipping/overlap, motion and narration/caption alignment where present, records issues and their fixes, and identifies the final main commit and reviewed outputs. The user has scheduled this work for the end; no human-review approval is required to continue with C.
