# P1.2-A — Disposable local render workers

Last updated: 2026-11-17

P1.2 starts with an opt-in Linux process boundary for snapshot PNG/MP4 rendering and browser layout measurement. A hung renderer can be cancelled or timed out, its detached browser descendants are terminated/reaped, and the same host can render again. The canonical project, tool permissions, execution ledger and Artifact publication stay in the parent host.

This is the delivered A step in the [five-step P1.2 plan](P1.2-PLAN.md). [PR #8](https://github.com/xxbo/ScienceMotion-AI/pull/8) merged it as `b4e5bc9`; [main CI #44002989900](https://github.com/xxbo/ScienceMotion-AI/actions/runs/44002989900) passed 223 tests and all real-render regressions. [B1's ledger](P1.2-B1-JOB-LEDGER.md) and [B2's asynchronous host/client APIs](P1.2-B2-HOST-JOBS.md) are now implemented. [B3](P1.2-B3-CLI-LIFECYCLE.md) now exercises protocol 1.1 with these actual workers through cancellation, process/temp cleanup and interrupted-host recovery; the A replay below remains a separate historical-protocol regression.

## First increment

- `openCreativeHost({directory, renderWorker: {}})` enables the worker adapter. The stdio server accepts the same optional `renderWorker` field in its trusted launch config. Custom renderer injection and worker configuration are mutually exclusive. Omitting the option retains the in-process path.
- Each operation gets an immutable JSON request and a private temporary directory. A new Node renderer uses the existing generic Remotion composition. Only trusted application configuration chooses code/entrypoints; AI tool arguments contain snapshot IDs and frame/range parameters.
- The parent limits concurrency, elapsed job time, request bytes and returned output bytes. It passes `--max-old-space-size` to the Node renderer. A worker cannot succeed until its child tree exits, its bounded regular output file is read, and the SHA-256/size plus project/revision/snapshot identity match the receipt.
- Cancellation reaches preview/video/layout requests from the invocation and session signals. Parent timeout or cancellation sends TERM, followed by a forced-termination request after the grace period. Late success cannot replace the terminal cancellation/timeout. Admission stays occupied and cancellation/deadlines remain active through real cleanup, before any result is returned.
- Render publication now checks authorization/cancellation **before** writing bytes. A legacy renderer that ignores cancellation cannot publish a late result when it eventually returns. The existing check after storage admission remains; cancellation during an already-admitted storage write still follows the existing uncertainty/reconciliation rules.
- Trusted applications can observe job lifecycle and coarse bundling/selecting/rendering/encoding progress through `onRenderWorkerEvent`. Observer exceptions cannot change results. Media receipts record the local-process job ID, guardian PID and elapsed time separately from the underlying Remotion renderer identity.

## Why the guardian exists

Remotion launches Chromium in a separate process group. Killing only the Node renderer's group would leave an unreliable cleanup boundary. Each job therefore starts a small Python 3 guardian configured with Linux `PR_SET_CHILD_SUBREAPER`. When the renderer exits, detached/orphaned descendants are adopted by this guardian. It terminates and reaps them before exiting, on successful completion as well as failure.

The guardian signals only its direct children. Their PIDs cannot be reused before this single-threaded process reaps them. It enumerates PPids through procfs because `/proc/<pid>/task/<tid>/children` is unavailable in some containers. It also requests a parent-death signal and checks its parent during startup. The application never SIGKILLs the guardian itself: a force request tells it to SIGKILL and reap remaining descendants. B3 also makes the surviving guardian remove its private job directory after parent death; normal output reads and cleanup remain owned by a living parent.

This requires **Linux, procfs, Python 3, Node.js/tsx and the existing renderer dependencies**. Unsupported platforms fail explicitly. It is not a container or third-party-code sandbox: the processes run with the same OS identity, inherited environment and filesystem/network access. The A adapter itself does not recover an interrupted host ledger; [B3](P1.2-B3-CLI-LIFECYCLE.md) supplies the explicit recovery workflow and its boundaries. Survival of a killed guardian and a strict real-time bound on uninterruptible OS I/O remain outside these guarantees.

## Policy and public boundary

| Field | Default | Allowed range / meaning |
| --- | --- | --- |
| `timeoutMs` | 30,000 | 1–300,000 ms; existing Gateway/tool deadlines still apply |
| `maxConcurrentJobs` | 1 | 1–4; excess direct adapter work is rejected, not silently queued |
| `maxOutputBytes` | 32 MiB | 1 KiB–64 MiB, further capped by the host Artifact limit |
| `maxOldSpaceMb` | 1,024 | 128–4,096 MiB of Node V8 old-space |
| `killGraceMs` | 150 | 0–1,000 ms before forced descendant termination |
| `preparedBundle` | Build per job | Trusted absolute directory and SHA-256 identity. [Prepared bundle reuse](P1.2-E2-BUNDLE-REUSE.md). |

Requests are capped at 12 MiB; IPC evidence at 8 KiB. Output checks reject missing, non-regular, linked, truncated, oversized or hash-mismatched files. These are output/admission limits, not a temporary-disk quota. The Node heap flag does not bound total RSS or Chromium/FFmpeg memory. CPU quotas and aggregate memory/disk limits remain later P1.2 work.

```ts
const host = await openCreativeHost({
  directory: "/path/to/workspace",
  renderWorker: { timeoutMs: 30_000, maxConcurrentJobs: 1 },
  onRenderWorkerEvent: event => recordProgress(event), // application-owned observer
});
// Pass signal inside the session.invoke invocation object, or call session.revoke().
// host.close() continues to stop admission and drain existing work.
```

The historical protocol-1.0 stdio dispatch remains sequential. SIGINT/SIGTERM revoke its session and drain the worker; a `close` request queued behind an invocation does not interrupt that invocation. A itself introduced no asynchronous endpoint. B2/B3 add protocol-1.1 background jobs and short control requests outside the render execution path; legacy `invoke` retains its serial behavior.

## Evidence

The original eight focused tests exercise verified success, observer failures, CPU work ignoring cancellation, detached descendants on success/crash/cancel, forced deadlines, a result sent by a process that refuses to exit, late results, cancellation during temporary-file cleanup, admission recovery, protocol/hash/size faults, symlink output, invalid policy/pre-aborted work and the host's no-late-publication guard. They execute real child processes using a deliberately faulty renderer fixture.

`npm run accept:render-worker` replays all 52 requests from the historical AI trial through the **actual stdio CLI with worker mode enabled**, in a fresh workspace. It retains two 12-second MP4s and five PNGs, rechecks model/layout diagnostics, verifies immutable snapshot data and per-job render receipts, fully decodes media and checks the same targeted text/motion pixels. This is deterministic regression with zero new model calls; the original interactive trial remains unchanged.

The scenario then reopens that workspace through the public host, starts a real 360-frame Remotion video, waits for nonzero rendering progress, observes the live process tree, and cancels it. It verifies terminal cancellation evidence, no new Artifact, unchanged project data, and that every observed process—including Chromium and FFmpeg—was reaped. A new preview at frame 45 must then succeed. The initial local run observed and reaped 10 processes; this count is environment-specific, not an assertion about every renderer environment.

Evidence is written to `out/ai-trial-worker/` and uploaded as `render-worker-evidence`, including on scenario failure. It contains the separate replay transcript, original/replay media checks, lifecycle progress, observed process identities, cancellation ledger record and recovery preview. Existing in-process AI replay, two-topic restore/plugin-switch, chart, layout and narrated-video checks continue in the same CI job.
