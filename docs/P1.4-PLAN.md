# P1.4 — Provider-independent creative planning

Last updated 2026-11-24

Run an approved brief through planning, revisioned tool calls, inspection, targeted repair and verified delivery. Reuse the [Creative Host](P1.1-F-CREATIVE-HOST.md) for discovery, authority and execution, and the [P1.3 short](P1.3-PLAN.md#f--integrated-inspection-and-repair) as a scripted baseline. Project Graph remains the creative state. Renderers consume snapshots through the existing host.

## A — Planning interface

Call `planCreativeStep(session, planner, { brief, query?, signal? })` from a trusted application. Supply the approved brief and a bounded project session. The `CreativePlanner` adapter receives the brief, the session project ID and a copy of one `session.discover` page with its exact tool versions, schemas and pagination. Use the existing query fields to select the relevant page. The adapter returns one [JSON decision](../schemas/creative-planner-decision.schema.json) under planner protocol `1.0.0`.

| Decision | Required data | Meaning |
| --- | --- | --- |
| `invoke` | `toolId`, `toolVersion`, `input` | Propose one call using a tool from the supplied page. |
| `finish` | `summary` | Propose ending the planning step. |
| `needs-input` | `question` | Identify information needed to proceed. |

The proposal limit is 1 MiB of UTF-8 JSON. Preflight rejects extra decision fields, non-finite data, tools outside the page and mismatched versions. It rechecks the selected manifest and validates the proposed input with the same schema validator settings as the Gateway. The signal reaches the adapter, and preflight checks cancellation before returning. The application owns invocation identity, work budgets and grants. Preflight reads discovery and manifests. The Gateway and Host remain authoritative for any later invocation, including project ownership, revision conflicts and limits.

```sh
npm run typecheck
npx tsx --test src/platform/creative-planner.test.ts
```

The tests exercise real Creative Host sessions with local adapter fixtures. A valid proposal leaves an empty project until the test explicitly submits it through the session. Rejection cases cover a restricted grant, page selection, version drift, invalid schema input and authority fields. Cancellation and terminal decisions are also checked.

## B — Bounded execution

Call `runCreativePlan(session, planner, { brief, query?, signal?, limits? })` from a trusted application. The runner pins one discovery page for the run, calls A's preflight on each proposal and uses the scoped session for each invocation. A successful tool call or a confirmed failure supplies the next turn's `observation`, with the previous decision, `callId` and `ToolResult`. The Host checks the exact selected version again at invocation.

The runner assigns a fresh `runId` and a `callId` for each attempted tool submission. It returns the pinned versions, accepted decisions, recorded results, attempted turn count, elapsed time and stop reason. The run ID and call IDs let the application match the trace to the Host execution ledger. Tool outputs and inputs identify any produced revision or snapshot. A planner can request `finish` or `needs-input` with the final summary or question in its decision.

Defaults are `maxTurns: 32`, `timeoutMs: 30000` and `maxOutputBytes: 1048576`. The byte budget counts compact UTF-8 JSON of each retained decision and result, with record metadata outside that count. If a decision would exceed the budget, stop before submitting it. If a confirmed result would exceed the budget, record its byte count and success flag, then stop before the next proposal. The application can configure positive integral limits when it starts a run.

The deadline and caller cancellation stop further submissions and signal the adapter and active invocation. When a submitted call lacks a confirmed result, or the result reports publication uncertainty, the stop is `outcome-unknown` and identifies the call. Look up its ledger record and current project revision before attempting another write. Host execution and storage settle under their existing cancellation and publication rules.

```sh
npm run accept:p1-4-b
```

The local adapter starts by reading the project. It creates the project in response to a confirmed missing-project result, selects remaining edits from each subsequent read and saves the observed revision of the two-shot CPU cache draft. The scenario reopens the workspace, verifies the snapshot hash and matches each call to its persisted input hash and result. A second run discards the response to a successful create. The runner stops after that call, and the reopened Host confirms the committed revision in the ledger. CI publishes both traces, the reopened draft and the execution records as `creative-run-evidence`.

## C — Inspection and repair

Call `repairCreativeSnapshot(session, planner, { snapshotId, brief, checks?, maxRepairs?, limits?, signal? })` with a retained snapshot. The controller runs through B's same scoped session. It reads the snapshot and uses all three inspectors by default. Supply `checks` to select `model`, `layout` and `timeline` independently. Model and layout accept explicit `frames`. Timeline accepts the existing range and the `requireNarrationForCaptions` option to measure declared narration coverage.

The repair planner receives the verified snapshot, reports and finding ranges, plus the supported edit manifests available to the session. Each proposal is one edit against the checked revision and one diagnosed target. Existing tools enforce schemas, permissions and revision guards.

| Evidence | Scoped edit |
| --- | --- |
| Model or layout bounds | Resize a diagnosed shape, path or chart using `graphics.2d.edit`. |
| Motion bounds | Change the position value of an existing key sampled in the diagnosed interval using `animation.keyframes.edit`. |
| Text overflow | Resize the diagnosed text component using one `project.patch.apply` node update. |
| Caption gaps | Trim a complete diagnosed leading or trailing gap using `timeline.edit`. The caption text and covered portion are preserved. |

The controller verifies snapshot hash and revision lineage. It reuses the baseline's actual inspected frames and timeline range, including when the baseline used automatic sampling. It rejects truncated or noncomparable evidence. A candidate becomes the latest verified checkpoint when a targeted finding loses occurrences and every remaining occurrence fits inside the preceding verified ranges. The report identifies the latest verified checkpoint, any comparable rejected candidate, unresolved findings and the full execution trace. Candidate revisions and the retained checkpoints are available through the Host. An application with restore permission can promote a retained checkpoint through `project.snapshot.restore`.

The default repair budget is three proposals within B's turn and output budgets and a 90-second deadline. A repair limit of zero permits an inspection-only run. Regression, no progress, a repeated edit, a stale revision or exhausted budget produces an explicit stop. Callers can use run and call IDs to reconcile an unconfirmed write.

```sh
npm run accept:p1-4-c
```

The deterministic CPU-cache scenario repairs an offscreen animation key, a clipped chart and a caption gap. It then opens the saved original and repaired snapshots after restarting the Host. The fault scenarios preserve the verified fallback when a candidate expands a finding, stop a repeated edit after partial improvement, reject a stale revision and stop when the repair budget is exhausted. CI publishes the reports, retained snapshots and execution records as `creative-repair-evidence`.

## D — Preview and delivery checks

Call `verifyCreativeDelivery(session, artifacts, { approved, repair?, range?, maxPreviewFrames?, reviewer?, timeoutMs?, signal? })` from a trusted Node application with FFmpeg and ffprobe available. Pass the retained snapshot's `id`, `revisionId` and `contentHash` as `approved`. When a repair report is supplied, its latest verified checkpoint must match that approval. Grant `project.snapshot.inspect`, `render.preview` and `render.video` with `snapshot.read` and `artifact.write`. Provide the Host's artifact store reader to resolve the retained job outputs.

Delivery defaults to the first sequence and accepts an explicit range of up to 900 frames within that sequence. It selects eight preview frames by default, with a configurable limit from one to twelve. The controller samples findings, shot boundaries, crossfades, caption boundaries and the export range in a repeatable order. The report records why each selected frame was included and how many candidates were omitted.

For each PNG and MP4, the controller checks the exact job request, snapshot, output receipt and artifact bytes. It decodes one RGBA frame per preview and every RGB frame of the MP4, and checks the approved dimensions, frame rate, frame count and duration. An in-range narration clip with positive gain requires an audio stream. Present audio is decoded to interleaved PCM, with sample-count tolerance for the final AAC block. The report retains the receipts and decoded hashes. The default deadline is 120 seconds. Cancellation stops further submissions and requests cancellation of an admitted active render. If the Host cannot confirm the stop request, the error identifies the job for inspection.

An optional application-supplied `reviewer` receives the verified previews. Its advisory observations are recorded with the approved snapshot, frame number and exact PNG artifact identity. The application owns review decisions. The final human acceptance workstream owns presentation review.

After reopening the Host, restore the approved snapshot through `project.snapshot.restore` and save the new revision. Call `verifyCreativeDeliveryRecovery(session, artifacts, { reference, restored, timeoutMs?, signal?, reviewer? })` with the prior trusted delivery report and the new retained snapshot identity. Recovery checks the restore revision and authored graph, renders the same range and frames, and compares the decoded preview pixels, video frames and audio samples. Matching decoded hashes require a compatible render and decode environment.

```sh
npm run accept:p1-4-d
```

The CPU-cache fixture repairs an offscreen marker and delivers eight representative PNGs and an eight-second narrated MP4. A local preview adapter checks the supplied PNGs and records frame-scoped observations. The scenario reopens the job ledger, restores the approved snapshot and repeats delivery in worker mode after the original WAV import file has been removed. CI publishes the repair and delivery reports with both sets of media as `creative-delivery-evidence`.

## E — End-to-end acceptance

Use two approved topics with the same runner and tool contracts. Include a narrated short with a scene transition. Preserve a bounded failure trace, the diagnostic and repair evidence, preview and export receipts, and reopened results. Report planning turns, tool calls, elapsed time, encoded frame counts and reported model usage when available. Keep deterministic CI runs and any real provider trial identifiable by their run provenance. Engineering delivery follows the [PR and main CI checks](PLAN.md#main-is-the-delivery-baseline).
