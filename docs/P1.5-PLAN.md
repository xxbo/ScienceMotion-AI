## A — Interfaces and baseline

### Tool handoffs

The runner retains exact manifest versions and passes a confirmed invocation result as the next planner observation. The application can use the execution ledger to reconcile an uncertain invocation by project, run and call ID. Plugins receive scoped host services. [Runner contract](P1.4-PLAN.md#b--bounded-execution) · [Host services](P1.1-F-CREATIVE-HOST.md).

| Producer | Evidence to carry | Consumer and check |
| --- | --- | --- |
| Project, scene, node and animation tools | Project and object IDs, and the returned revision ID | Subsequent tools target the existing objects. Revision-guarded edits use the observed revision as `baseRevisionId`. |
| `assets.import` | Project asset ID and its retained artifact identity | Timeline tools place the project asset ID. Render services resolve and verify the retained bytes. |
| `project.snapshot.save` | Snapshot ID and content hash with the revision used to save it | Inspect and deliver from the retained snapshot. Confirm its revision and hash by reading the snapshot. |
| `inspect.snapshot`, `inspect.layout`, `inspect.timeline` | Snapshot, revision and finding identities with explicit coverage | Repair only a diagnosed target and recheck the same coverage on a retained candidate. |
| `render.preview` and `render.video` jobs | Exact snapshot, frame or range, profile, renderer ID/version and output receipt | Verify the artifact hash and decoded media. On reopen, recover the named snapshot and verify a new render of the same range. |

The B scenario uses this path for a real producer and consumer from different plugins. The application supplies grants and pins tool versions through the existing Host. Rejected calls preserve the previous retained checkpoint and carry a diagnostic in the run trace.

### Engine boundary

`openCreativeHost({ renderer })` accepts one trusted `ProjectGraphSnapshotRenderer` per Host instance. Its requests contain an immutable Project Graph, revision and snapshot hash, plus a frame or range. Its responses carry PNG or MP4 bytes and the adapter identity. Browser layout measurement is optional in the interface. Host jobs record the engine identity in the admitted input and verified receipt. [Renderer contract](../src/contracts/renderer.ts) · [Job evidence](P1.2-B2-HOST-JOBS.md).

| Capability | Current Remotion implementation | Target for the SVG and FFmpeg adapter |
| --- | --- | --- |
| Scene and geometry | Project Graph 2D text, shapes, paths, charts, groups and PNGs | One shot with a flat list of opaque, filled rectangles, ellipses and circles in draw order |
| Animation and timeline | Supported keyframe properties, shot selection, cuts and crossfades | Scene-local linear position keys on the reference geometry |
| Media and inspection | PNG layers, WAV narration, timed captions and browser layout measurement | Silent rendering of a shape-only graph, with common model and timeline inspection |
| Outputs | PNG preview and H.264 MP4 | PNG preview and H.264 MP4 from the same profile and requested range |

The second adapter is scoped to SVG rasterization via FFmpeg's `librsvg` decoder and H.264 encoding via `libx264`. A local toolchain probe rendered the reference shapes at frame 40 to a PNG with matching interior colors and encoded a three-frame MP4 at 10 fps. C verifies the adapter through the Host, including a descriptive failure for an unsupported capability before publishing artifacts.

### Reference workload

`water-motion-v1` derives from the approved, repaired evaporation scene in the recorded P1.4 water-cycle trial. A source check verifies the recorded repair report's file hash, the checkpoint identity and the source Project Graph hash. The fixture retains the background rectangle, water ellipse, rising circle and its original three position keys. It records the source separately and has its own revision and snapshot identity. [Fixture and workload](../examples/water-motion-baseline.json) · [Trial manifest](ai-trials/p1-4-water-loop-2026-11-24/manifest.json).

The snapshot contains one 80-frame shot at 640 × 360 and 10 fps. The benchmark requests PNG frame 40 and MP4 frames `[12, 52)`. Each video contains 40 frames over four seconds. Output checks decode the entire media and sample the expected marker positions at frames 12, 40 and 51. They also check the water and background colors and verify that the previous marker positions clear. The PNG samples use exact RGBA values. The decoded H.264 samples permit eight levels of per-channel difference at interior points. Later comparisons use these invariants across engines and compare decoded hashes within each engine.

### Repeat the baseline

Use Linux, installed project dependencies, the configured Remotion browser and system FFmpeg and ffprobe. The source check runs before the benchmark. [P1.2 sampling method](P1.2-E1-PERFORMANCE-BASELINE.md).

```sh
npm run bench:p1-5-a
```

The default three samples each use a fresh Node process, private workspace and empty bundle cache, with installed dependencies and browser shared. Each sample runs the first PNG, repeat PNG, first MP4 and repeat MP4 in that order on the same Remotion renderer. Both MP4 requests use the bundle initialized by the first PNG. Timings span the renderer request through settlement and record the observed bundling, selection and render phases. Process-tree CPU, sampled peak RSS and disk use cover the whole sample. The system FFmpeg verification runs after measurement.

The report includes the checkout and installed versions, per-sample timings, decoded media hashes and the reference files from the first sample. CI uploads `render-engine-baseline` from `out/render-engine-baseline/`. The summary gives medians and observed ranges. Timing varies with the runner. The media checks are the CI acceptance gate. [CI workflow](../.github/workflows/video-engine.yml).
